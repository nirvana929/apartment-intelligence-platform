# AptInsight 技术架构与模块设计

## 1. 总体架构

AptInsight 分为两个阶段实现。

## 2. 第一阶段架构：独立 Agent 服务

第一阶段不接入现有后台，先独立验证能力。

```text
调试入口
  - Swagger
  - Postman
  - 简单测试页面
        |
        v
Python FastAPI: aptinsight-agent
        |
        +--> LLM 服务
        |
        +--> Schema/指标知识库
        |
        +--> SQL 安全校验器
        |
        +--> MySQL 只读连接池
        |
        v
现有 MySQL 业务数据库
```

第一阶段特点：

1. 开发快。
2. 调试方便。
3. 不影响现有 Spring Boot 和 Vue 代码。
4. 可以集中验证 Text-to-SQL 准确率。

## 3. 第二阶段架构：后台集成

第二阶段通过现有 Spring Boot 后端接入。

```text
Vue3 管理后台
        |
        | POST /admin/ai/chat
        v
Spring Boot web-admin
        |
        | HTTP 调用
        v
Python FastAPI aptinsight-agent
        |
        | SELECT only
        v
MySQL 业务数据库
```

集成原则：

1. 前端不直接调用 Python Agent。
2. Spring Boot 继续负责登录鉴权、统一返回、异常封装。
3. Python Agent 只负责智能分析，不负责后台用户权限。
4. 数据库使用独立只读账号。

## 4. 技术选型

AptInsight AI 项目使用独立 AI 工程技术栈，不和现有 `least` Java 后端混在一个工程中。选型原则是：优先解决 AptInsight 的真实问题，其次体现 AI Agent 工程能力。现有 Spring Boot 只在第二阶段作为集成网关调用 Agent。

| 层 | 技术 | 阶段 | 采用原因 |
| --- | --- | --- | --- |
| AI 服务运行时 | Python 3.12 | MVP | AI Agent 生态成熟，适合独立服务 |
| 包管理 | `uv` | MVP 推荐 | 依赖锁定、安装快，便于演示和 CI |
| API 服务 | FastAPI + Pydantic v2 | MVP | 暴露 `/chat`、`/health`，请求响应强校验 |
| Agent 编排 | LangGraph | MVP 核心 | Text-to-SQL 有意图路由、安全失败、SQL 修复、空结果等分支，需要状态图管理 |
| 模型接入 | OpenAI-compatible client | MVP | 先接一个兼容模型即可 |
| 模型网关 | LiteLLM | 后期推荐 | 需要多模型供应商、模型切换、降级时再引入 |
| 数据库连接 | SQLAlchemy 2.x async + asyncmy | MVP | 连接现有 MySQL，只读查询 |
| SQL 解析校验 | sqlglot | MVP 核心 | 解析 AST，限制只读查询、表白名单和敏感字段 |
| 数据处理 | Pandas | MVP | 查询结果小，足够做表格、统计和图表映射 |
| 数据处理 | Polars | 后期可选 | 数据量明显变大或批处理增强时再引入 |
| 配置管理 | pydantic-settings | MVP | `.env`、环境变量、类型校验 |
| 日志 | JSON logs + trace_id | MVP | 方便定位一次问题从提问到 SQL 执行的链路 |
| 可观测性 | OpenTelemetry + Prometheus | 后期增强 | 生产部署或多人使用后再接入 |
| 测试 | pytest + Agent Eval Harness | MVP 核心 | 回归 SQL 生成、SQL 安全、指标口径、拒答能力 |
| 集成测试 | Testcontainers | 后期推荐 | CI 需要隔离 MySQL 环境时再引入 |
| 代码质量 | Ruff + pre-commit | MVP 推荐 | 成本低，保证格式和基础质量 |
| 类型检查 | MyPy | 后期推荐 | 代码量增长后再强制 |
| 容器化 | Docker | 集成阶段推荐 | 部署和演示环境一致，但不阻塞 MVP |
| 本地编排 | Docker Compose | 集成阶段可选 | 需要一键启动 Agent + 测试 MySQL 时使用 |
| CI/CD | Harness Pipeline as Code | 企业化加分 | 将 pytest 和 Agent Eval Harness 接入企业流水线 |
| 安全扫描 | pip-audit / Trivy | 企业化加分 | 依赖和镜像进入交付流程时启用 |

核心取舍：

1. **LangGraph 必须保留**，因为 AptInsight 的 Agent 流程有明确状态、分支和失败恢复，不是简单问答。
2. **Agent Eval Harness 必须保留**，因为 prompt、schema、few-shot 一改就可能影响 SQL，必须可回归。
3. **Docker 和 Harness CI/CD 不作为 MVP 前置条件**，但作为集成演示和企业化交付能力保留。
4. **Kubernetes、Prometheus、OpenTelemetry 不放入第一阶段**，避免把项目做重。

现有系统保留：

| 层 | 技术 | 作用 |
| --- | --- | --- |
| 后台前端 | Vue3、TypeScript、Element Plus、ECharts | 第二阶段新增智能运营分析页面 |
| Java 后端 | Spring Boot 3.0.5、MyBatis-Plus、JWT | 第二阶段新增 `/admin/ai/chat` 网关接口 |

## 6. 模块职责

### 6.1 API 层

职责：

1. 接收用户问题。
2. 校验请求参数。
3. 创建 trace_id。
4. 调用 Agent 主流程。
5. 返回统一 JSON。

不做：

1. 不拼 SQL。
2. 不直接处理复杂业务逻辑。
3. 不暴露数据库账号信息。

### 6.2 意图路由模块

职责：

1. 判断问题是否属于公寓运营分析。
2. 判断是否需要查库。
3. 判断问题类型：查询、趋势、占比、诊断、指标解释、拒答。

输出示例：

```json
{
  "intent": "data_query",
  "domain": "appointment",
  "need_sql": true,
  "need_chart": true,
  "time_range": "current_month"
}
```

### 6.3 Schema 知识库

职责：

1. 向模型说明表名、字段、枚举、关系。
2. 向模型说明指标口径。
3. 存放 few-shot 示例。

知识库不需要向量化也能完成第一版。第一版建议直接把精简后的 schema 和指标口径放入 prompt。

### 6.4 SQL 生成模块

职责：

1. 将自然语言问题转换为 MySQL SELECT。
2. 使用表别名。
3. 默认加 `is_deleted = 0`。
4. 默认加 `LIMIT`。
5. 避免返回敏感字段。

### 6.5 SQL 安全校验模块

职责：

1. 解析 SQL。
2. 只允许单条 SELECT。
3. 禁止 DDL/DML。
4. 禁止多语句。
5. 限制表白名单。
6. 限制敏感字段。
7. 自动补充最大返回行数。

校验失败时不执行 SQL。

### 6.6 数据库执行模块

职责：

1. 使用只读账号执行 SQL。
2. 设置查询超时。
3. 限制最大返回行数。
4. 返回列名、列类型、行数据、耗时。

### 6.7 结果分析模块

职责：

1. 判断结果是否为空。
2. 判断指标高低、排名、趋势。
3. 计算简单变化率。
4. 生成结构化摘要，供最终回答使用。

### 6.8 图表生成模块

职责：

1. 根据结果列类型选择图表。
2. 生成 ECharts option。
3. 控制图表字段映射。

图表选择规则：

| 数据形态 | 图表 |
| --- | --- |
| 日期/月份 + 数值 | 折线图 |
| 类别 + 数值 | 柱状图 |
| 状态 + 数量/占比 | 饼图 |
| 多列明细 | 表格 |
| 无数值列 | 表格 |

### 6.9 回答生成模块

职责：

1. 基于查询结果生成中文总结。
2. 明确数据口径。
3. 给出 1 到 3 条运营建议。
4. 对缺失数据给出说明。

要求：

1. 不编造 SQL 结果之外的数据。
2. 不给绝对化判断。
3. 不返回敏感信息。

## 7. 主流程

```text
1. 接收 question
2. 参数校验
3. 意图识别
4. 如果是指标解释，直接回答
5. 如果不支持，返回拒答
6. 组装 schema + metric + few-shot prompt
7. LLM 生成 SQL
8. SQL 安全校验
9. 必要时 SQL 修复
10. 执行 SQL
11. 结果格式化
12. 生成图表
13. 生成业务总结
14. 返回 JSON
15. 记录日志
```

## 9. 数据库账号

必须使用只读账号。

示例：

```sql
CREATE USER 'ai_readonly'@'%' IDENTIFIED BY 'change_me';
GRANT SELECT ON least.* TO 'ai_readonly'@'%';
FLUSH PRIVILEGES;
```

如果实际库名是 `lease`，则替换为：

```sql
GRANT SELECT ON lease.* TO 'ai_readonly'@'%';
```

## 10. 安全设计

### 10.1 SQL 层安全

必须满足：

1. 只允许 SELECT。
2. 只允许一条语句。
3. 禁止 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`TRUNCATE`。
4. 禁止 `information_schema`、`mysql`、`performance_schema`、`sys`。
5. 禁止 `SELECT *` 返回宽表。
6. 禁止返回密码、身份证号。
7. 默认 `LIMIT 200`。
8. 查询超时中断。

### 10.2 服务层安全

第一阶段：

1. 服务只监听本地或内网。
2. 调试接口增加简单访问 token。
3. 不提交 `.env`。

第二阶段：

1. Python Agent 只允许 Spring Boot 访问。
2. Spring Boot 复用当前 `access-token`。
3. 前端不保存大模型 API Key。

### 10.3 隐私保护

默认不返回：

1. 密码。
2. 身份证号。
3. 完整手机号。
4. 过长备注。

如需要展示用户手机号，应在 SQL 层使用脱敏表达式：

```sql
CONCAT(LEFT(phone, 3), '****', RIGHT(phone, 4)) AS phone_masked
```

## 11. 性能设计

第一版数据量较小，重点控制安全和稳定。

建议限制：

| 项 | 默认值 |
| --- | --- |
| 最大返回行数 | 200 |
| SQL 查询超时 | 10 秒 |
| LLM 调用超时 | 30 秒 |
| 单次问题最大长度 | 500 字 |
| 图表最大分类数 | 30 |

当结果超过限制时返回 warning：

```text
结果较多，已默认展示前 200 行。请增加时间范围或地区筛选条件。
```

## 12. 日志设计

建议记录：

| 字段 | 说明 |
| --- | --- |
| `trace_id` | 单次请求 ID |
| `session_id` | 会话 ID |
| `user_id` | 后台用户 ID，独立阶段可为空 |
| `question` | 用户问题 |
| `intent` | 意图类型 |
| `generated_sql` | 生成 SQL |
| `safe_sql` | 最终执行 SQL |
| `status` | success / failed |
| `error_message` | 错误原因 |
| `duration_ms` | 总耗时 |
| `row_count` | 返回行数 |
| `created_at` | 创建时间 |

第一阶段可以写文件日志；第二阶段可新增数据库表 `ai_query_log`。

## 14. 与现有后端的关系

现有后端继续负责：

1. 登录。
2. 权限。
3. 统一返回 `Result<T>`。
4. 业务管理接口。
5. 转发 AI 请求。

AptInsight 不替代现有 CRUD 接口，只提供分析能力。

## 15. 与现有前端的关系

现有前端继续使用：

1. Vue Router 静态路由。
2. Pinia 用户状态。
3. Axios 封装。
4. Element Plus UI。
5. ECharts 图表库。

集成时只需要新增：

1. `src/api/aptInsight/index.ts`
2. `src/api/aptInsight/types.ts`
3. `src/views/aptInsight/index.vue`
4. 路由菜单项 `智能运营分析`
