# AptInsight 系统升级路线与缺陷改进

版本：v0.1
日期：2026-05-02
适用范围：AptInsight 独立 Agent 服务、Text-to-SQL 工作流、评测体系和后续后台集成

## 1. 文档目标

本文档记录 AptInsight 从“可运行的 Text-to-SQL MVP”升级为“更像客服助手的运营分析系统”需要补强的方向。

当前系统已经具备基础链路：

```text
用户问题 -> 意图识别 -> SQL 生成 -> SQL Guard -> 执行查询 -> 图表/回答生成
```

但当前链路偏一次性执行：模型生成一条 SQL 后直接执行，执行为空或语义偏差时，系统缺少反思、修正和澄清机制。后续升级重点不是让模型无限自由思考，而是增加受控的诊断和恢复节点。

## 2. 当前核心问题

### 2.1 一次性 SQL 生成缺少执行后反思

现象：

1. 用户问题表达不够精确时，模型会直接猜字段和过滤条件。
2. SQL 执行返回 0 行时，系统直接回答“没有找到符合条件的数据”。
3. 系统不会判断是数据库确实没有数据，还是 SQL 条件过严、字段映射错误、时间范围错误。

典型案例：

```text
用户问题：大学城哪个公寓的房源最多
错误 SQL 条件：ai.district_name = '大学城'
实际问题：district_name 存的是“番禺区”等行政区，“大学城”更可能是地址、商圈、学校或片区关键词。
```

期望行为：

```text
第一次查询为空后，系统应判断“大学城”不是明确行政区字段，
自动尝试 name/address_detail/district_name 的模糊匹配，或反问用户确认范围。
```

### 2.2 地点词映射规则不足

自然语言里的地点词不总是数据库字段里的行政区。

| 用户说法 | 可能含义 | 不应直接映射为 |
| --- | --- | --- |
| 大学城 | 地标、片区、地址关键词 | `district_name = '大学城'` |
| 北亭 | 公寓名、社区、地址关键词 | 固定某个区县 |
| 番禺区 | 行政区 | 地址全文搜索 |
| 某公寓名称 | 公寓名 | 区县 |

升级规则：

1. 省、市、区县等明确行政区可以使用等值匹配。
2. 学校、商圈、社区、街道、地标、模糊片区优先使用 `name`、`address_detail`、`district_name` 的 `LIKE` 匹配。
3. 当无法判断地点词类型时，应进入澄清流程，而不是强行生成精确 SQL。

### 2.3 排名类问题的返回粒度不稳定

现象：

用户问“哪里最多”“哪个最高”时，模型有时返回排行榜 `LIMIT 10`，有时返回单条 `LIMIT 1`。

建议规则：

| 用户表达 | 默认 SQL 行数 | 说明 |
| --- | --- | --- |
| 哪个最多 / 哪个最高 / 第一名 | `LIMIT 1` | 直接回答最优项 |
| 哪些最多 / 排名 / TOP | `LIMIT 10` | 返回排行榜 |
| 各 X 的 Y | 不强制 `LIMIT 1` | 返回分组结果 |

回答层即使拿到多行，也应该主动总结第一名，而不是让用户自己从表格里判断。

### 2.4 回答生成 fallback 信息损失

当前 `write_answer` 在答案生成失败时会进入 fallback。fallback 只展示前 3 个字段，容易漏掉核心指标字段，例如 `room_count`、`avg_rent`、`max_rent`。

已发现缺陷：

```text
答案生成失败: Logger._log() got an unexpected keyword argument 'answer_length'
```

影响：

1. 正常 LLM 回答生成被打断。
2. `summary` 为空或质量下降。
3. fallback 答案可能只列名称和地址，漏掉最关键的数值。

升级方向：

1. 修复日志调用方式。
2. fallback 必须优先展示指标列。
3. 排名类 fallback 应明确写出第一名和指标值。

### 2.5 当前 session_id 不等于记忆能力

当前请求体支持 `session_id`，但代码只把它放入 state 或日志，没有读取历史对话，也没有把历史消息拼入 LLM prompt。

结论：

```text
当前系统没有真正的多轮记忆。
```

后续如需记忆，应做轻量、可控的会话状态，而不是把完整历史无条件塞给模型。

推荐记忆内容：

1. 最近一次明确的地域过滤条件。
2. 最近一次业务对象，例如公寓、房间、租约、预约。
3. 最近一次指标，例如房源数、租金、预约量。
4. 最近一次时间范围。

不推荐记忆：

1. 整段历史自然语言。
2. 上一次生成的 SQL 直接复用。
3. 不确定的模型推断条件。

## 3. 升级原则

### 3.1 受控反思，不做无限 ReAct

数据库查询系统需要安全、可解释和可回归。后续可以引入反思节点，但必须限制次数和行为范围。

建议策略：

```text
SQL 执行为空 -> repair_sql 最多一次 -> 再过 SQL Guard -> 再执行一次
```

禁止策略：

```text
模型无限循环思考、无限生成 SQL、绕过 SQL Guard、自动扩大到敏感字段。
```

### 3.2 不确定时先澄清

当问题缺少必要约束，或自动修正风险较高时，应生成澄清问题。

示例：

```text
我没有确认“大学城”在系统里是行政区、地址关键词还是公寓名称。
你想按地址关键词搜索，还是按具体区县搜索？
```

### 3.3 Prompt、规则、评测一起升级

每次改进不能只改 prompt。需要同步更新：

1. 生成规则或知识库。
2. 评测用例。
3. 失败样例记录。
4. 回归报告。

### 3.4 默认快路径，异常慢路径

反思和修正能力会增加耗时和模型调用成本，因此不能让所有问题都走完整多步链路。

推荐原则：

```text
普通问题走快路径，异常问题才进入慢路径。
```

快路径：

```text
用户问题 -> 意图识别 -> SQL 生成 -> SQL Guard -> 执行 SQL -> 回答
```

慢路径只在必要时触发：

```text
SQL 执行 0 行
SQL Guard 拒绝但可修复
问题包含模糊地点词
问题包含容易混淆的指标词
字段映射不确定
```

慢路径：

```text
异常结果 -> 规则诊断 -> 可程序化修复则修复 SQL -> SQL Guard -> 再执行一次
                         -> 不可程序化修复则生成澄清问题
```

成本控制策略：

1. 优先用规则诊断，不优先调用 LLM。
2. 可程序化修复的问题，不额外调用 LLM。
3. `repair_sql` 最多触发一次。
4. 不确定时优先澄清，而不是反复生成 SQL。
5. 所有修复后的 SQL 仍必须经过 SQL Guard。

典型低成本修复：

```text
如果 SQL 中出现 district_name = '大学城' 且结果为 0 行，
可改成 name/address_detail/district_name 的 LIKE 模糊匹配。
```

典型可疑 SQL 检查：

```text
如果用户问“最高”，但 SQL 使用 AVG，且用户没有明确说“平均”，
应标记为指标语义可疑，进入修正或澄清。
```

## 4. 用户意图理解层技术方案

当前最需要升级的是用户意图理解层。目标不是让模型自由发挥更多，而是在 SQL 生成前把用户问题转换成可检查、可解释、可回归的结构化语义。

### 4.1 目标架构

推荐将当前链路：

```text
用户问题 -> classify_intent -> generate_sql
```

升级为：

```text
用户问题
  -> classify_intent
  -> normalize_question
  -> entity_mapper
  -> metric_resolver
  -> ambiguity_detector
  -> generate_sql
  -> semantic_guard
  -> SQL Guard
  -> execute_sql
```

说明：

1. `classify_intent` 判断大类，不负责理解所有细节。
2. `normalize_question` 输出结构化语义帧。
3. `entity_mapper` 负责把用户词映射到业务实体和字段。
4. `metric_resolver` 负责把“最多、最高、平均、趋势”等词映射到指标口径。
5. `ambiguity_detector` 判断是否需要反问用户。
6. `semantic_guard` 在 SQL 执行前检查 SQL 是否符合用户原意。

### 4.2 结构化语义帧

新增 `SemanticFrame`，作为 SQL 生成前的中间表示。

示例：

```json
{
  "intent": "ranking_query",
  "subject": "apartment",
  "metric": "room_count",
  "aggregation": "count",
  "ranking": "top_1",
  "location": {
    "raw": "大学城",
    "type": "ambiguous_place",
    "match_strategy": "fuzzy"
  },
  "time_range": null,
  "filters": [
    {"field": "room_info.is_release", "operator": "=", "value": 1}
  ],
  "need_clarification": false,
  "confidence": 0.82
}
```

建议字段：

| 字段 | 作用 | 示例 |
| --- | --- | --- |
| `intent` | 查询类型 | `ranking_query` |
| `subject` | 业务对象 | `apartment`、`room`、`lease` |
| `metric` | 指标名 | `room_count`、`avg_rent`、`max_rent` |
| `aggregation` | 聚合方式 | `count`、`avg`、`max` |
| `ranking` | 排名意图 | `top_1`、`top_n`、`bottom_n` |
| `location` | 地点语义 | 原词、类型、匹配策略 |
| `time_range` | 时间范围 | 本月、最近 30 天 |
| `filters` | 确定过滤条件 | 已发布、未删除、已签约 |
| `need_clarification` | 是否需要澄清 | true/false |
| `confidence` | 理解置信度 | 0-1 |

### 4.3 意图类型扩展

当前 `analysis/chitchat/out_of_scope` 粒度过粗。建议扩展为：

| 意图 | 说明 | 是否查库 |
| --- | --- | --- |
| `data_query` | 普通数量、列表、详情查询 | 是 |
| `ranking_query` | 最多、最高、最低、排名 | 是 |
| `trend_analysis` | 趋势、走势、按月/日变化 | 是 |
| `distribution_analysis` | 分布、占比、构成 | 是 |
| `diagnosis` | 经营诊断、异常识别 | 是 |
| `metric_explanation` | 指标口径解释 | 否 |
| `clarification` | 需要反问用户 | 否 |
| `chitchat` | 闲聊或功能介绍 | 否 |
| `out_of_scope` | 超出范围或不安全 | 否 |

收益：

1. “哪个最多”稳定进入 `ranking_query`。
2. “各状态占比”稳定进入 `distribution_analysis`。
3. “怎么计算有效租约”进入 `metric_explanation`，不需要生成 SQL。
4. 不确定问题进入 `clarification`，避免乱查。

### 4.4 指标词典

建立 `Metric Registry`，不要让模型自由解释所有指标词。

示例：

```yaml
room_count:
  aliases: ["房源数量", "房间数量", "房源数", "房源最多"]
  subject: room
  table: room_info
  aggregation: COUNT
  field: id
  default_filters:
    - room_info.is_deleted = 0
    - room_info.is_release = 1

max_rent:
  aliases: ["租金最高", "最高租金", "最贵"]
  subject: room
  table: room_info
  aggregation: MAX
  field: rent
  forbidden_when_user_says: ["平均"]

avg_rent:
  aliases: ["平均租金", "均价"]
  subject: room
  table: room_info
  aggregation: AVG
  field: rent
```

关键规则：

1. 用户说“最高、最贵”时，不默认使用 `AVG`。
2. 用户明确说“平均”时，才使用 `AVG`。
3. 用户说“最多”时，应先判断对象是房源数、预约量、租约数还是浏览量。
4. 用户说“效果最好、质量最高”时，应进入澄清，因为指标不明确。

### 4.5 实体和字段映射

建立 `Entity Mapper`，把用户词映射到业务对象、字段和匹配策略。

| 用户词类型 | 示例 | 推荐映射 |
| --- | --- | --- |
| 行政区 | 番禺区、天河区 | `apartment_info.district_name = ?` |
| 城市 | 广州、深圳 | `apartment_info.city_name = ?` |
| 地标/学校/商圈 | 大学城、体育西、软件园 | `name/address_detail/district_name LIKE ?` |
| 公寓名 | 北亭学府公寓 | `apartment_info.name LIKE ?` |
| 房间号 | 101、A栋201 | `room_info.room_number LIKE ?` |
| 状态词 | 已发布、已签约、退租 | 枚举字段或布尔字段 |

地点词默认策略：

```text
明确行政区 -> 等值匹配
非明确地点词 -> 模糊匹配
无法判断 -> 澄清
```

### 4.6 歧义检测

新增歧义检测规则，避免模型强行猜。

需要澄清的典型表达：

| 用户表达 | 问题 | 澄清方向 |
| --- | --- | --- |
| 哪个最好 | 指标不明确 | 房源数、租金、预约量、评分？ |
| 附近 | 缺少中心点 | 哪个地址或公寓附近？ |
| 这个区域 | 依赖上下文 | 是否继承上一轮地点？ |
| 经营情况怎么样 | 范围过大 | 看预约、租约、租金还是空置？ |
| 热门公寓 | 热门口径不明确 | 浏览量、预约量还是签约量？ |

澄清响应建议：

```json
{
  "answer": "我需要确认一下：你说的“热门公寓”是按浏览量、预约量，还是签约量来判断？",
  "clarification_required": true,
  "clarification_options": ["按浏览量", "按预约量", "按签约量"]
}
```

### 4.7 SQL 语义校验

当前 SQL Guard 主要检查安全，后续需要增加 `semantic_guard` 检查 SQL 是否符合用户语义。

建议规则：

| 用户语义 | SQL 可疑模式 |
| --- | --- |
| 用户问“最高/最贵” | SQL 使用 `AVG`，且用户没说平均 |
| 用户问“平均” | SQL 没有 `AVG` |
| 用户问“哪个最多” | SQL 没有 `ORDER BY ... DESC` 或没有 `LIMIT` |
| 用户问“大学城” | SQL 直接使用 `district_name = '大学城'` |
| 用户问“房源/房间” | SQL 没有使用 `room_info` |
| 用户问“预约” | SQL 没有使用 `view_appointment` |
| 用户问“趋势” | SQL 没有时间字段聚合 |
| 用户问“占比/比例” | SQL 没有分子分母或分组统计 |

处理方式：

1. 低风险问题直接规则修复。
2. 中风险问题进入 `repair_sql`。
3. 高风险或不确定问题进入澄清。

### 4.8 Few-shot 策略

Few-shot 需要做，但不要只堆数量。优先补“对照样例”。

高价值对照样例：

| 易混问题 A | 易混问题 B | 目的 |
| --- | --- | --- |
| 各公寓平均租金是多少 | 租金最高的公寓是哪个 | 区分 `AVG` 和 `MAX` |
| 番禺区哪个公寓房源最多 | 大学城哪个公寓房源最多 | 区分行政区和模糊地点 |
| 哪些公寓预约量最高 | 哪个公寓预约量最高 | 区分 `LIMIT 10` 和 `LIMIT 1` |
| 当前租约状态占比 | 当前有效租约数量 | 区分分布和单值 |
| 最近 30 天预约趋势 | 本月预约量是多少 | 区分趋势和汇总 |

推荐策略：

1. P0 阶段可以先把关键 few-shot 直接放入 prompt。
2. P1 后根据 `SemanticFrame.intent/metric/subject` 选择 2-3 个相关 few-shot。
3. P4 再考虑关键词召回或向量召回。

### 4.9 与会话记忆的关系

意图理解层可以使用会话记忆，但只能使用结构化、确认过的信息。

允许继承：

```json
{
  "location": "番禺区",
  "location_type": "district",
  "subject": "apartment",
  "metric": "room_count"
}
```

禁止继承：

1. 上一次模型猜测出来但用户未确认的过滤条件。
2. 上一次生成的 SQL。
3. 完整自然语言历史。

当继承上下文时，回答中需要说明：

```text
我沿用上一轮的“番禺区”范围，为你查询租金最高的公寓。
```

### 4.10 推荐落地顺序

建议先做轻量版，不一次性实现完整复杂系统。

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| S1 | 指标词典 + 地点词规则 | 低成本解决最高/平均、大学城类问题 |
| S2 | `normalize_question` 输出 `SemanticFrame` | 稳定 SQL 生成输入 |
| S3 | `semantic_guard` | 在 SQL 执行前发现语义偏差 |
| S4 | 歧义检测和澄清问题 | 避免不确定时乱查 |
| S5 | 空结果诊断和规则修复 | 减少“没有找到数据” |
| S6 | few-shot 对照样例召回 | 提升复杂问题稳定性 |
| S7 | 轻量会话记忆 | 支持多轮客服式问答 |

验收标准：

1. 关键幻觉问题有对应 eval case。
2. SQL 安全检查和语义检查都通过后才执行。
3. 空结果不直接断言无数据，优先诊断是否匹配条件过严。
4. 不确定问题能反问用户。
5. 普通查询仍走快路径，不显著增加耗时。

## 5. 推荐升级路线

### P0：修复明确缺陷

目标：先解决已经影响调试体验的问题。

任务：

1. 修复 `write_answer` 中 logger 调用导致答案生成失败的问题。
2. 优化 fallback 答案，确保展示核心指标列。
3. 在租金类指标中补充“最高租金”和“平均租金”的区分。
4. 在 SQL 生成规则中补充地点词映射规则。

验收：

1. `warnings` 不再出现 `Logger._log() got an unexpected keyword argument`。
2. “大学城哪个公寓的房源最多”不再生成 `district_name = '大学城'` 这种过严条件。
3. “租金最高的公寓是哪个”能区分 `MAX(rent)` 和 `AVG(rent)`。

### P1：增加空结果修正节点

目标：解决“SQL 查不到就结束”的问题。

设计要求：P1 不应让所有查询都变慢。普通查询仍走快路径；只有 SQL 执行为空、SQL 可疑或字段映射不确定时，才进入诊断和修正链路。

新增节点建议：

```text
execute_sql
  -> has_rows: build_chart/write_answer
  -> empty_rows: diagnose_empty_result
  -> repairable: repair_sql
  -> need_clarification: ask_clarification
  -> unrecoverable: write_answer
```

`diagnose_empty_result` 判断维度：

1. 是否存在等值匹配的地点词。
2. 是否时间范围过窄。
3. 是否字段映射可能错误。
4. 是否业务对象和 schema 不匹配。
5. 是否可以通过规则直接生成更宽松但安全的 SQL。

`repair_sql` 限制：

1. 最多执行一次。
2. 仍然只能生成 `SELECT`。
3. 必须重新经过 SQL Guard。
4. 修正原因需要写入 `warnings` 或调试字段。

触发成本建议：

| 场景 | 处理方式 | 是否增加 LLM 调用 |
| --- | --- | --- |
| 普通查询有结果 | 直接回答 | 否 |
| 空结果且命中规则修复 | 程序化修 SQL，再查一次 | 否 |
| 空结果但原因复杂 | 调用一次 `repair_sql` | 是 |
| 字段/指标不确定 | 生成澄清问题 | 可选 |
| 修复后仍为空 | 停止修复，解释或澄清 | 否 |

### P2：增加澄清问题机制

目标：当模型无法可靠判断用户意图时，不强行查询。

适用场景：

1. 地点词不明确。
2. 用户问“那里”“这个区域”等依赖上下文的问题，但没有可用记忆。
3. 指标含义不明确，例如“效果最好”“质量最高”。
4. 数据库不支持该问题。

响应示例：

```json
{
  "answer": "我需要先确认一下：你说的“大学城”是地址关键词，还是某个具体区县？",
  "clarification_required": true,
  "clarification_options": ["按地址关键词搜索", "按区县搜索", "按公寓名搜索"]
}
```

### P3：轻量多轮记忆

目标：支持客服式连续提问，但避免历史污染 SQL。

建议状态结构：

```json
{
  "session_id": "1",
  "filters": {
    "location": "番禺区",
    "location_type": "district",
    "time_range": "最近30天"
  },
  "last_subject": "apartment",
  "last_metric": "room_count"
}
```

使用原则：

1. 只继承用户明确确认过的条件。
2. 每次继承条件时，在答案中说明。
3. 用户新问题出现冲突条件时，以新问题为准。
4. 不把上一轮 SQL 当作事实记忆。

### P4：Schema 和样例检索

目标：减少 prompt 过长和样例干扰。

当前问题：

1. few-shot 文件存在，但主流程未有效注入 SQL 生成 prompt。
2. 全量 schema 和指标容易让模型被不相关规则带偏。

升级方向：

1. 根据意图选择相关表、字段、指标。
2. 根据问题召回少量 few-shot。
3. 将“位置搜索”“最高/平均/排名”等高风险规则做成固定规则块。

### P5：评测体系升级

目标：让 prompt 改动可回归。

新增评测类型：

| 类型 | 示例 | 验证点 |
| --- | --- | --- |
| 地点模糊匹配 | 大学城哪个公寓房源最多 | 不直接 `district_name = '大学城'` |
| 精确行政区 | 番禺区哪个公寓房源最多 | 可以使用 `district_name = '番禺区'` |
| 最高 vs 平均 | 租金最高的公寓是哪个 | 使用 `MAX` 或 `ORDER BY rent DESC` |
| 空结果修复 | 不存在的精确地点 | 能澄清或给出可解释原因 |
| 闲聊回答 | 你好 / 你是谁 | 不返回“没有找到数据” |
