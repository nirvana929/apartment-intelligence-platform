## 2. 项目总览

整个仓库 `apartment-intelligence-platform` 是一个围绕公寓租赁业务构建的一体化平台，不只是普通 CRUD 系统，而是包含：

- 租赁业务后端：负责房源、预约、租约、用户、后台管理等核心业务。
- 管理后台前端：给运营人员管理房源、预约、租约和用户。
- 租客 H5 前端：给租客找房、看房源详情、预约、查看租约。
- C 端 AI 助手 AptGuide：面向租客，完成自然语言找房、规则问答、预约确认、租约查询。
- B 端 AI 助手 AptInsight：面向运营人员，完成自然语言数据分析、Text-to-SQL、图表和总结。

从面试角度看，三个项目的分工如下：

| 项目 | 面向角色 | 主要能力 | 面试价值 |
| --- | --- | --- | --- |
| AptGuide | 租客 C 端 | LLM-first 理解、RAG 推荐、业务工具调用、写操作确认 | 体现 AI Agent、RAG、业务流程编排、安全确认和端到端验证能力 |
| AptInsight | 运营 B 端 | Text-to-SQL、SQL Guard、LangGraph 工作流、Agent Eval | 体现 AI 后端、数据分析、安全治理、评测体系能力 |
| SmartLease | 公寓运营后台 | 房源、预约、租约、缓存、鉴权、文件存储、部署 | 体现 Java 后端基本功、业务建模、接口设计、状态流转和工程落地能力 |

推荐面试讲述顺序：

1. 先讲 SmartLease：这是业务底座，说明你理解租赁业务和后端系统。
2. 再讲 AptGuide：说明你如何把 AI Agent 接入真实业务流程。
3. 最后讲 AptInsight：说明你如何用 AI 做运营分析，并处理安全和评测问题。

如果面试岗位更偏 AI 应用开发，也可以先讲 AptGuide，再讲 AptInsight，最后用 SmartLease 证明后端基础。

## 3. AptGuide - 租客端智能找房助手

### 3.1 项目定位

AptGuide 是面向租客的 C 端智能找房助手。它服务的不是运营人员，而是普通租客，核心场景包括：

- 租客用自然语言描述找房需求。
- 租客咨询租房规则，例如押金、付款方式、租期规则。
- 租客预约看房或取消预约。
- 租客查询自己的预约或租约。
- 系统记住租客长期偏好，例如预算、区域、通勤、采光、是否接受合租等。
- 当 AI 无法处理时转人工。

它不是一个简单聊天机器人，而是一个接入租赁主系统的 AI Agent。它需要理解用户意图、检索知识、调用业务接口、管理会话状态，并且在写操作前要求用户确认。

### 3.2 平台链路

最终集成链路可以理解为：

```text
租客
  -> rentHouseH5 / AiAssistant
  -> lease web-app POST /app/ai/chat
  -> AptGuide POST /api/chat
  -> LLM / Milvus / Redis / MySQL / lease internal tools
```

各部分职责：

- `rentHouseH5`：用户入口，负责展示聊天 UI 和房源卡片。
- `lease web-app`：租客端业务后端，负责鉴权、转发 AI 请求、提供内部工具接口。
- `AptGuide`：Agent 服务，负责理解用户输入、流程编排、RAG、确认动作和回复生成。
- `Milvus`：向量数据库，用于房源语义召回和租房规则知识库检索。
- `MySQL`：持久化 Agent 状态，例如会话、消息、待确认动作、记忆、审计事件。
- `Redis`：保存热状态和 TTL 数据，例如会话缓存、待确认动作短期状态。
- `LLM`：负责自然语言理解、结构化输出、答案生成。

### 3.3 简历上的技术栈怎么讲

| 技术 | 在项目中的作用 | 面试讲法 |
| --- | --- | --- |
| Python | AI 服务主体语言 | AI 生态成熟，适合快速构建 LLM、RAG、评测和服务端逻辑 |
| FastAPI | 对外提供 `/api/chat`、`/health`、`/ready` 等接口 | 类型友好、异步支持好、适合 AI 后端服务 |
| RAG | 规则问答和房源推荐增强 | 解决模型不知道业务知识、容易编造的问题 |
| Milvus | 向量检索 | 存储房源和规则知识的向量，支持语义召回 |
| Embedding | 把文本转成向量 | 让自然语言需求和房源/知识文档可以做语义匹配 |
| MySQL | 持久化 Agent 状态 | 保存会话、消息、待确认动作、记忆、审计和 trace |
| Redis | 热状态和 TTL | 管理短期状态，提高读取效率，适合待确认动作过期控制 |
| SQLAlchemy | Python 侧数据库访问 | 用 ORM / repository 封装持久化层 |
| Playwright | 前端 E2E 测试 | 验证真实浏览器中的聊天、卡片渲染和流程交互 |

### 3.4 核心设计一：LLM-first 结构化理解

简历写法：

> 设计 LLM-first 结构化理解方案，将用户输入解析为任务类型、硬性条件、软偏好、检索查询和风险等级；低置信度或语义矛盾时进入澄清流程。

这句话背后的含义：

传统做法可能用关键词路由，例如看到“预约”就进入预约流程，看到“租约”就进入租约流程。但这种方式很容易误判：

- “我不想预约了”不能直接创建预约。
- “我预算不是 3000，是 2500”不能简单识别成找 3000 元房源。
- “有没有不用押一付三的房子”既可能是规则咨询，也可能是找房条件。

AptGuide 采用 LLM-first：

1. 用户输入先交给 LLM 做结构化理解。
2. 模型输出结构化字段，例如：
   - `task_type`：找房、规则问答、预约、租约、记忆、转人工、澄清。
   - `hard_constraints`：硬性条件，如预算上限、区域、户型、租期。
   - `soft_preferences`：软偏好，如采光好、安静、离地铁近。
   - `retrieval_queries`：用于向量检索的查询语句。
   - `risk_level`：是否涉及写操作、敏感信息或高风险动作。
   - `confidence`：模型对理解结果的置信度。
3. 后端对结构化结果做 schema 校验。
4. 如果 JSON 无法解析、字段矛盾、置信度低或风险高，就不继续执行，而是向用户澄清。

面试重点：

- LLM 负责语义理解，但不能直接决定所有动作。
- 代码负责契约校验、安全边界、权限、写操作确认。
- 低置信度时宁愿追问，也不要误执行。

### 3.5 核心设计二：7 类业务 Procedure

AptGuide 不是所有问题都走同一套逻辑，而是拆成多个 typed procedure：

| Procedure | 作用 |
| --- | --- |
| clarify | 澄清用户需求，例如预算、区域、租期不明确 |
| room_search | 找房推荐，根据条件和偏好检索房源 |
| kb_qa | 租房规则问答，例如押金、付款方式、看房流程 |
| appointment | 预约看房、取消预约、查询预约 |
| lease | 查询租约、合同、入住相关信息 |
| memory | 记住或更新用户偏好 |
| handoff | 转人工 |

这样拆分的好处：

- 每个流程职责清晰。
- 更容易测试。
- 更容易做权限和风险控制。
- 后续扩展新流程时不会把所有逻辑塞进一个巨大函数。

面试可以这样说：

> 我把 Agent 当成业务流程编排器，而不是简单的一次模型调用。模型先做结构化理解，后端再根据任务类型进入不同 procedure，每个 procedure 有自己的输入契约、状态更新、工具调用和回复生成逻辑。

### 3.6 核心设计三：RAG 检索与推荐链路

简历写法：

> 实现 RAG 检索与推荐链路，支持多查询向量召回、业务房源校验、加权排序和置信度门控。

完整链路可以拆成：

1. 需求理解：从用户输入中提取预算、区域、户型、通勤、采光、安静等条件。
2. 查询改写：生成一个或多个检索 query，例如：
   - “天河区 2500 元以内 一居室”
   - “靠近地铁 安静 采光好”
   - “适合通勤到珠江新城的房源”
3. 向量召回：用 Embedding 将 query 转成向量，在 Milvus 中召回语义相关房源。
4. 业务校验：向量召回结果必须再调用 lease 后端校验，例如房源是否上架、是否可租、价格和状态是否真实。
5. 加权排序：综合硬性条件、软偏好、语义相关度、业务状态、价格匹配等维度排序。
6. 置信度门控：如果结果质量不够高，不能强行推荐，要说明限制或继续澄清。
7. 回复生成：把推荐理由、房源卡片、下一步动作返回给前端。

为什么不能只靠向量召回？

- 向量相似只代表文本相关，不代表房源真实可租。
- 房源价格、状态、预约情况可能变化。
- 业务事实必须以后端数据库为准。

为什么需要置信度门控？

- AI 推荐如果没有把握，强行输出会损害用户信任。
- 对低质量召回结果，系统应该澄清、放宽条件或说明没有合适结果。

### 3.7 核心设计四：写操作确认

简历写法：

> 预约创建、取消和偏好记忆写入均通过待确认动作完成，保证写操作可控。

这里的核心思想是：LLM 不能直接执行写操作。

写操作包括：

- 创建预约。
- 取消预约。
- 写入长期偏好记忆。
- 可能影响用户业务状态的操作。

正确流程：

```text
用户表达意图
  -> LLM 识别为写操作
  -> 后端生成 pending action
  -> 返回给用户确认
  -> 用户明确确认
  -> 后端再调用 lease 工具或写入 memory
  -> 记录审计事件
```

这样做的原因：

- LLM 可能误解用户意图。
- 用户可能只是询问，不是真的要操作。
- 业务写入必须可追踪、可审计、可撤销或可解释。

面试可答：

> 我把“理解意图”和“真正执行业务写操作”拆开。Agent 先生成待确认动作，只有用户明确确认后才执行，并记录审计事件。这样可以避免模型误判导致错误预约或错误写入长期偏好。

### 3.8 状态持久化与边界

AptGuide 维护的是 Agent 状态，不替代租赁主系统。

AptGuide 负责：

- 会话 session。
- 消息 message。
- 待确认动作 pending action。
- 用户偏好 memory。
- 人工转接 ticket。
- trace 事件。
- procedure run。
- audit event。

lease 主系统负责：

- 用户身份。
- 房源数据。
- 公寓数据。
- 预约记录。
- 租约和合同。
- 敏感业务数据。

边界很重要：

- AptGuide 不能直接成为业务事实来源。
- 房源、预约、租约等事实必须通过 lease 内部工具接口读取或写入。
- 前端不能直接访问 Milvus、MySQL、Redis 或 LLM。

### 3.9 测试与验证

项目中可以讲的验证方式：

- 单元测试：验证 procedure、理解契约、RAG 排序、状态管理等。
- Live RAG 集成测试：验证 Milvus、Embedding、知识库和召回链路。
- Playwright E2E：验证前端聊天页面和卡片渲染。
- 依赖健康检查：检查 MySQL、Redis、lease、Milvus、LLM、Embedding 等依赖是否可用。
- readiness endpoint：通过 `/ready?live=true` 判断真实依赖是否就绪。

表达要稳妥：

- 可以说“完成阶段性验证，覆盖单元测试、Live RAG 集成测试、前端 E2E 和依赖健康检查”。
- 不建议说“所有测试全部通过、生产全量上线”，除非现场能完全证明。

### 3.10 AptGuide 高频面试题

#### Q1：为什么不用关键词路由？

关键词路由容易误判用户真实意图。例如“我不想预约了”如果只看“预约”两个字，可能误进入预约流程。我的做法是让 LLM 输出结构化理解结果，再由后端做 schema 校验、置信度判断和风险判断。低置信度或语义矛盾时进入澄清流程，而不是硬猜。

#### Q2：RAG 在你的项目里解决什么问题？

RAG 主要解决两个问题：第一，租房规则、房源描述等业务知识不能完全依赖模型记忆；第二，房源推荐需要根据用户语义偏好找到相关候选。通过 Embedding 和 Milvus 做语义召回，再结合业务后端校验和排序，降低模型编造和推荐不准确的问题。

#### Q3：为什么向量召回后还要业务校验？

因为向量召回只说明文本语义相关，不说明房源真实可用。房源是否上架、价格是否变化、是否可预约、是否已出租，这些事实必须以后端数据库为准。所以我会通过 lease 内部工具接口做业务校验。

#### Q4：写操作为什么要 pending action？

LLM 可能误解用户意图，所以不能让模型理解到“预约”就直接创建预约。pending action 把识别意图和真正写入业务系统隔离开，用户确认后才执行，并记录审计事件。

#### Q5：用户偏好记忆怎么做？

用户表达长期偏好后，系统先提取 memory candidate，再生成待确认动作。用户确认后写入 memory repository。后续找房时，会合并当前输入和历史偏好，但当前输入优先级更高，避免旧记忆覆盖新需求。

#### Q6：如果 RAG 没检索到合适房源怎么办？

不能强行编造结果。可以返回没有合适结果的原因，引导用户放宽预算、区域、租期等条件，或进入澄清流程。对于低置信度结果，要通过置信度门控控制输出。

## 4. AptInsight - 公寓运营智能分析助手

### 4.1 项目定位

AptInsight 是面向公寓后台运营人员的智能分析助手。运营人员不需要手写 SQL，而是用自然语言提问，例如：

- 最近 7 天预约量是多少？
- 哪些公寓浏览热度最高？
- 当前可租房源有多少？
- 本月租约签约情况怎么样？
- 哪些房源可能存在转化率低的问题？

系统负责将自然语言转换成安全的只读 SQL，查询 MySQL 后返回：

- 表格数据。
- 图表数据。
- 运营总结。
- 必要时说明无法回答的原因。

它的重点不是普通问答，而是 Text-to-SQL + 安全治理 + 评测体系。

### 4.2 核心链路

```text
运营人员自然语言问题
  -> 意图识别
  -> SQL 生成
  -> SQL Guard 安全校验
  -> 只读 MySQL 执行
  -> 结果脱敏
  -> 图表构建
  -> 答案总结
```

这个链路体现了一个重要思想：AI 生成 SQL 只是中间步骤，不能直接执行。

### 4.3 简历上的技术栈怎么讲

| 技术 | 在项目中的作用 | 面试讲法 |
| --- | --- | --- |
| Python / FastAPI | AI 后端服务 | 提供 `/api/chat` 和健康检查接口 |
| LangGraph | 编排 Text-to-SQL 工作流 | 把意图识别、SQL 生成、安全校验、执行、总结拆成可观测节点 |
| Text-to-SQL | 自然语言转 SQL | 降低运营人员查询数据的门槛 |
| MySQL | 业务数据库 | 存储公寓、房间、预约、租约等业务数据 |
| SQLAlchemy / asyncmy | 异步数据库访问 | 执行只读 SQL，提高服务端工程化程度 |
| sqlglot | SQL AST 解析与校验 | 比正则更可靠地识别 SELECT、表、字段、危险语句 |
| Pydantic | 结构化输入输出 | 约束 API 响应、LLM 输出和内部状态 |
| Qwen | LLM | 负责意图理解、SQL 生成和答案总结 |
| Agent Eval | 评测体系 | 固化测试集，回归业务、安全和边界场景 |

### 4.4 为什么使用 LangGraph

Text-to-SQL 不是一次 LLM 调用就结束。真实系统需要处理很多分支：

- 用户问题是否和业务相关？
- 数据库是否有这个字段？
- SQL 是否只读？
- 是否访问敏感字段？
- 查询结果为空怎么办？
- SQL 执行失败怎么办？
- 查询结果适合什么图表？
- 最终总结是否和结果一致？

LangGraph 的价值是把流程拆成节点：

| 节点 | 职责 |
| --- | --- |
| intent recognition | 判断用户问题类型、是否可回答 |
| sql generation | 根据 schema、指标口径和 few-shot 生成 SQL |
| sql guard | 校验 SQL 是否安全、是否符合白名单 |
| query execution | 使用只读账号执行 SQL |
| chart builder | 根据结果构建图表配置 |
| answer generation | 用自然语言总结结果 |

这样做的好处：

- 每个节点可测试。
- 每次请求有 trace，方便定位问题。
- 安全校验可以独立于模型输出。
- 后续优化某个节点不会影响整个系统结构。

### 4.5 SQL Guard 设计

简历写法：

> 基于 sqlglot 实现 AST 级 SQL Guard，限制只允许 SELECT 查询，拦截多语句、系统库、危险操作和敏感字段访问，并结合表/字段白名单和只读账号降低数据风险。

为什么需要 SQL Guard？

因为 LLM 生成 SQL 不可靠，可能生成：

- `DELETE`、`UPDATE`、`DROP` 等危险语句。
- 多语句 SQL，例如 `SELECT ...; DROP TABLE ...;`
- 访问系统库。
- 查询敏感字段，如密码、身份证、手机号明文。
- 查询不存在的表或字段。

为什么用 sqlglot，而不是正则？

- SQL 语法复杂，正则很容易漏掉子查询、别名、多语句、大小写变化和绕过写法。
- sqlglot 可以把 SQL 解析成 AST，更准确地判断语句类型、表名、字段名和表达式结构。

SQL Guard 的多层防护：

1. 只允许 SELECT。
2. 拒绝多语句。
3. 拒绝系统库。
4. 表白名单。
5. 字段白名单。
6. 敏感字段拦截。
7. 结果脱敏。
8. 数据库账号只读。

面试可以强调：

> 我没有把安全完全交给 prompt，而是在模型输出之后做确定性的 AST 校验，并且数据库账号本身也是只读权限。即使模型生成错误 SQL，也不能破坏业务库。

### 4.6 Schema、指标口径和 few-shot

Text-to-SQL 的难点不只是让模型写出 SQL，而是让它写出符合业务含义的 SQL。

项目中需要整理：

- 数据库有哪些表。
- 表之间怎么关联。
- 字段含义是什么。
- 枚举值如何解释。
- 逻辑删除字段是什么。
- 时间字段应该用哪个。
- 指标如何计算。
- 哪些问题不能回答。

例如：

- “已发布公寓”可能需要 `is_release = 1 AND is_deleted = 0`。
- “有效租约”需要判断租约状态，而不是简单 count 所有记录。
- 如果数据库没有支付流水，就不能回答“实际收款金额”。
- 如果预约表没有 room_id，就不能直接回答“某个房间预约量最高”。

few-shot 的作用：

- 给模型提供典型问题和 SQL 示例。
- 约束模型使用正确表、字段和过滤条件。
- 降低模型编造字段的概率。

### 4.7 Agent Eval Harness

简历写法：

> 构建 Agent Eval Harness，覆盖 40 个业务分析、安全测试和边界拒答场景；最终评测通过率 87.5%，安全用例通过率 100%，核心指标口径通过率 100%。

为什么需要评测？

AI 应用的行为受 prompt、模型、schema 描述、few-shot、温度参数影响。修改任何一处，都可能导致 SQL 生成变化。如果只靠人工试几个问题，无法保证稳定。

评测集覆盖：

- 业务分析问题：预约、租约、租金、浏览热度、公寓、房间等。
- 安全问题：危险 SQL、敏感字段、越权查询、多语句。
- 边界问题：数据库没有的数据、无关问题、无法回答的问题。
- 指标口径：确保核心指标计算方式正确。

关键结果：

- 40 个测试场景。
- 总通过率 87.5%。
- 安全用例 100%。
- 核心指标口径 100%。

面试表达要点：

- 安全类必须 100%，否则不能上线。
- 业务类可以逐步提升，但要有评测基线。
- 评测不是一次性工作，而是 prompt 和模型迭代的回归机制。

### 4.8 AptInsight 高频面试题

#### Q1：为什么要做 Text-to-SQL？

运营人员经常有临时数据分析需求，但他们不一定会写 SQL。如果每次都找开发写查询，效率很低。Text-to-SQL 可以让运营用自然语言查询预约、租约、房源、租金等数据，并返回表格、图表和总结。

#### Q2：Text-to-SQL 最大风险是什么？

最大风险是模型生成错误或危险 SQL。错误 SQL 会导致分析结论错误，危险 SQL 可能破坏数据或泄露敏感信息。所以需要 SQL Guard、只读账号、白名单、脱敏和评测体系。

#### Q3：为什么 SQL Guard 用 AST？

正则对 SQL 的理解太弱，容易被大小写、换行、注释、子查询、别名、多语句绕过。AST 能解析 SQL 结构，更可靠地识别语句类型、表、字段和危险操作。

#### Q4：如何防止模型编造字段？

我会把数据库 schema、字段含义、指标口径和 few-shot 提供给模型，同时在 SQL Guard 中做表字段白名单。如果模型生成不存在或不允许访问的字段，校验阶段会拒绝执行。

#### Q5：如果用户问数据库没有的数据怎么办？

不能编造。系统应该识别当前 schema 是否支持这个问题，如果没有相关字段或表，就返回无法基于当前数据回答，并说明缺少什么数据。例如没有支付流水表时，不能回答实际收款金额。

#### Q6：为什么要做 Agent Eval？

因为 AI 应用不是传统确定性函数，prompt、模型和 schema 一变化就可能影响结果。Agent Eval 可以把核心业务、安全和边界场景固定下来，每次修改后回归，保证系统质量不会退化。

## 5. SmartLease - 租赁业务管理平台

### 5.1 项目定位

SmartLease 是面向公寓运营的租赁业务管理平台，是整个平台的业务底座。它负责传统后端核心能力：

- 房源管理。
- 公寓管理。
- 看房预约。
- 签约。
- 续约。
- 退租。
- 租客用户管理。
- 图片上传。
- 登录鉴权。
- 缓存。
- 部署。

从面试角度看，SmartLease 用来证明你不是只会调用大模型，而是具备完整后端工程能力，包括业务建模、接口设计、数据库设计、状态流转、缓存、鉴权、文件存储和部署。

### 5.2 技术栈怎么讲

| 技术 | 在项目中的作用 | 面试讲法 |
| --- | --- | --- |
| Spring Boot | 后端服务框架 | 快速构建 RESTful API 和业务服务 |
| MyBatis-Plus | ORM / 数据访问 | 简化 CRUD、分页查询和条件构造 |
| MySQL | 业务数据存储 | 保存公寓、房间、预约、租约、用户等核心数据 |
| Redis | 缓存和 Token 管理 | 缓存热点房源、管理登录态或验证码等短期数据 |
| JWT | 用户鉴权 | 无状态登录凭证，前后端分离常用方案 |
| MinIO | 对象存储 | 保存房源图片等文件资源 |

| Linux | 部署环境 | 体现服务部署、配置和运维基础 |

### 5.3 核心业务建模

租赁业务核心实体包括：

- 公寓：位置、名称、状态、配套、标签等。
- 房间：所属公寓、户型、价格、面积、朝向、状态等。
- 用户：租客、运营人员、后台账号。
- 预约：租客预约看房的时间、房源、状态。
- 租约：签约、续约、退租、租期、租金等。
- 图片/附件：房源图片、合同附件等。

业务关系：

- 一个公寓有多个房间。
- 一个房间可以被多个用户浏览或预约，但同一时间只能有合法租赁状态。
- 一个用户可以有多个预约。
- 一个用户可以有租约记录。
- 租约和房间状态相互影响。

面试时要重点讲清楚：

- 表不是孤立 CRUD，而是围绕租赁流程设计。
- 状态字段很重要，例如房间是否可租、预约是否待看房、租约是否有效。
- 接口层要做状态约束，不能只依赖前端。

### 5.4 租约状态流转

简历写法：

> 设计租约状态流转并在接口层做状态约束，保证签约、续约、退租等流程的一致性与数据正确性。

可讲的状态包括：

- 待签约。
- 已签约 / 生效中。
- 即将到期。
- 已续约。
- 已退租。
- 已取消。

状态约束示例：

- 未签约的租约不能退租。
- 已退租的租约不能续约。
- 已取消的预约不能再次确认。
- 房间已出租时不能重复签约。

为什么状态流转重要？

- 租赁业务不是简单增删改查。
- 错误状态会导致业务数据混乱，例如一个房间同时被两个租客签约。
- 后端必须兜底校验，不能只靠前端按钮控制。

面试可以这样讲：

> 我会把租约流程看成状态机。每个接口只能允许合法状态进入下一状态，例如签约后才能续约或退租，已退租后不能再续约。这样可以避免并发或前端绕过导致的数据不一致。

### 5.5 Redis 使用

Redis 在 SmartLease 中主要用于：

- 热点房源缓存。
- Token / 登录态管理。
- 短信验证码或临时数据。

热点房源缓存的意义：

- 房源列表和详情访问频繁。
- 对热门房源做缓存可以减少数据库压力。
- 对更新频率不高但读取频繁的数据比较适合。

缓存要注意的问题：

- 缓存一致性：房源更新后要删除或更新缓存。
- 过期时间：避免长期脏数据。
- 缓存穿透：不存在的数据被频繁访问。
- 缓存击穿：热点 key 过期瞬间大量请求打到数据库。

面试可以准备：

> 我使用 Redis 缓存热点房源和管理 Token。对于房源缓存，更新房源时需要清理对应缓存，查询时先查缓存，未命中再查 MySQL 并回写。对于登录态，Redis 可以支持过期控制和主动失效。

### 5.6 JWT 鉴权

JWT 的作用：

- 用户登录成功后生成 token。
- 前端后续请求携带 token。
- 后端拦截器解析 token，获取用户身份。
- 对需要登录的接口做权限校验。

JWT 的优点：

- 适合前后端分离。
- 服务端不一定需要保存 session。
- token 中可以包含用户 ID、角色、过期时间等。

JWT 的注意点：

- token 泄露会带来安全风险。
- 需要设置过期时间。
- 如果需要主动踢下线，可以结合 Redis 做 token 黑名单或登录态管理。

### 5.7 MinIO 和 Nginx

MinIO：

- 用于存储房源图片等文件。
- 避免把图片二进制直接存数据库。
- 后端负责上传、生成访问地址、保存元数据。

Nginx：

- 反向代理后端接口。
- 部署前端静态资源。
- 可以统一域名、端口和路径。
- 可以做 gzip、缓存、跨域等配置。

### 5.8 SmartLease 高频面试题

#### Q1：这个项目主要难点是什么？

不是单表 CRUD，而是租赁业务流程建模。房源、预约、租约之间有关联，签约、续约、退租都有状态约束。后端需要保证状态流转合法，避免前端绕过或并发操作导致数据错误。

#### Q2：租约状态怎么设计？

可以把租约看成状态机，不同接口只能在特定状态下执行。例如待签约可以签约，生效中可以续约或退租，已退租不能再续约。接口层做状态校验，保证数据一致性。

#### Q3：为什么用 Redis？

一方面缓存热点房源，减少数据库压力；另一方面可以管理 Token、验证码等有过期时间的临时数据。Redis 适合读写快、需要 TTL 的场景。

#### Q4：JWT 和 Redis Token 管理有什么关系？

JWT 可以作为无状态身份凭证，但如果需要主动失效、踢下线或控制登录态，可以把 token 或 token 标识存到 Redis 中，配合过期时间和黑名单机制。

#### Q5：MinIO 为什么不用数据库存图片？

数据库适合结构化数据，不适合存大量图片二进制。MinIO 是对象存储，适合存房源图片，数据库只保存文件 URL、对象 key 和元数据。

#### Q6：这个项目和两个 AI 项目的关系是什么？

SmartLease 是业务底座。AptGuide 调用它的内部工具接口获取房源、预约、租约等业务事实；AptInsight 读取它的业务数据做运营分析。没有 SmartLease，两个 AI 项目就缺少真实业务数据和操作对象。

## 6. 三个项目的横向联系

### 6.1 一句话讲清楚整体平台

这是一个围绕公寓租赁业务构建的平台：SmartLease 提供房源、预约、租约等业务底座；AptGuide 面向租客，把自然语言找房、规则问答和预约操作接入业务流程；AptInsight 面向运营人员，把自然语言数据分析转成安全只读 SQL，辅助运营决策。

### 6.2 为什么这不是简单套壳 AI

可以从四点回答：

1. 有真实业务系统：房源、预约、租约、用户、后台管理。
2. 有业务边界：AI 不直接改业务库，写操作需要确认。
3. 有检索和校验：RAG 召回后还要业务后端校验。
4. 有评测和安全：Text-to-SQL 有 SQL Guard 和 Agent Eval。

### 6.3 AI 项目共同方法论

两个 AI 项目都体现了同一个思路：

- LLM 适合做语义理解、生成和总结。
- 确定性代码负责边界、安全、权限、校验和执行。
- 数据库和业务系统负责事实。
- 测试和评测负责持续回归。

可以总结为：

> 模型负责理解和生成，系统负责约束和落地。

### 6.4 面试官可能横向追问

#### Q1：AptGuide 和 AptInsight 有什么区别？

AptGuide 面向租客，是 C 端交互型 Agent，重点是找房推荐、规则问答、预约确认、记忆和工具调用。AptInsight 面向运营人员，是 B 端分析型 Agent，重点是 Text-to-SQL、安全查询、图表和运营总结。

#### Q2：两个 AI 项目都用到数据库，区别是什么？

AptGuide 的业务事实来自 lease 工具接口，自己主要保存 Agent 状态，不直接作为房源和租约事实来源。AptInsight 使用只读 MySQL 查询业务数据，重点是安全分析，不做业务写入。

#### Q3：你如何保证 AI 不乱来？

分层控制：输入理解要结构化，输出要 schema 校验；写操作要 pending action；SQL 要 AST Guard；业务事实要后端校验；数据库账号只读；关键场景要用测试和 eval 回归。

#### Q4：你最想强调的技术亮点是什么？

如果是 AI 应用岗位，重点强调：

- LLM-first 结构化理解。
- RAG 推荐链路。
- 写操作确认。
- SQL Guard。
- Agent Eval。

如果是 Java 后端岗位，重点强调：

- 租赁业务建模。
- 状态流转。
- Redis 缓存和 Token。
- MinIO 文件存储。
- AI 与 Java 主系统的边界集成。
