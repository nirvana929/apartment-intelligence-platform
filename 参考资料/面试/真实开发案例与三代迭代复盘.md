## 三、案例一：初版 AptGuide 多轮状态污染与确认流程 Bug

### 事实背景

初版 AptGuide 使用 LangGraph 组织 `intent -> slot -> ask -> kb_search -> room_search -> rerank -> confirm -> tool -> reply` 流程，并在会话中维护卡片、回复和确认状态。

### 真实问题 A：无关问题仍弹出上一轮预约卡片

**现象：**

用户上一轮搜索房源后，下一轮即使询问与找房无关的问题，系统仍展示上一轮的房源/预约卡片。

**根因：**

`chat.py` 的 session 状态在请求之间没有清理临时输出字段。上一轮 `rerank_node` 设置的 `cards` 和 `reply` 残留到下一轮，`reply_node` 判断已有回复和卡片后直接透传旧结果。

**解决：**

在每次图执行前重置临时字段，例如 `reply`、`cards`、`actions`、`sources`、`search_results` 和 `intent`。

### 真实问题 B：修复污染时不能清掉 confirmation

**现象：**

如果为了清理状态而同时把 `confirmation` 清空，用户下一轮点击“确认”时，系统无法读取待确认操作，预约流程断裂。

**根因：**

`confirmation` 不是临时展示字段，而是一个跨轮次任务状态：上一轮生成、下一轮消费。

**解决：**

临时输出字段在请求开始时重置；`confirmation` 保留到 `tool_node` 或取消逻辑真正消费后再清除。

### 你能讲出的工程认识

> 这个问题让我意识到，多轮 Agent 的状态不能简单按“全部保留”或“全部清空”处理。需要区分展示型临时状态和需要跨轮保留的任务状态。像卡片和回复应该每轮重置，而待确认动作必须有明确生命周期，直到确认、取消或过期后才能清理。

### 推荐回答版本

> 在初版 AptGuide 中我遇到过一个多轮状态管理问题：用户上一轮搜索了房源，下一轮去问规则问题时，页面仍然弹出上一轮房源的预约卡片。排查后发现，会话中用于展示的 `cards` 和 `reply` 没有在新请求开始时清理，导致回复节点透传了旧结果。我把这类临时字段改为每轮重置。  
> 但修复过程中我还发现，不能简单把所有状态都重置，因为预约确认依赖上一轮产生的 `confirmation`。最终我把状态分成临时展示状态和跨轮任务状态，确认信息只在用户确认或取消后消费清除。这让我对 Agent 多轮 workflow 中的状态生命周期有了更具体的理解。

## 四、案例二：AptGuide 初版接入真实业务接口的契约问题

### 真实问题

在 AptGuide 和 `lease` Java 后端联调时，项目记录了多项契约不一致问题：

| 问题 | 后果 | 修复方向 |
| --- | --- | --- |
| AI 服务一度从请求 body 使用 `user_id` | 可能允许伪造用户身份查询预约或租约 | 改为读取可信请求头 `X-User-Id`，忽略 body 伪造值 |
| Java 工具返回驼峰字段，AI 侧按下划线字段取值 | 预约/租约卡片字段为空 | 做字段映射兼容 |
| AptGuide 2.0 使用 `Authorization: Bearer` 调 lease | 内部接口返回 `401` | 改为 `X-Internal-Token` |
| AI 客户端预期成功码 `0`，lease 返回 `200` | 正常响应被误判为失败 | 接纳 `0` 与 `200` 契约 |
| 区域 ID 映射不一致 | “天河区/番禺区”可能查询不到正确业务数据 | 对齐 query understanding 与 lease 枚举值 |

### 面试价值

这个案例比抽象说“我做了工具调用”更有说服力，因为它体现了 AI 服务接真实后端时，真正困难的是身份、字段、状态码与业务枚举契约对齐。

### 推荐回答版本

> 在将租客 Agent 接入 Java 业务后端时，我遇到过一组典型的服务契约问题。例如 AI 侧最初对内部鉴权头、成功响应码和区域 ID 的理解与 lease 后端不一致，导致认证失败或查询结果异常；另外用户身份不能信任前端 body 传值，否则查询个人预约和租约会有越权风险。  
> 我在这个过程中形成的认识是，Agent 不能绕过业务网关直接“自由调用工具”，工具层必须有清晰的鉴权头、用户上下文、DTO 字段和错误码契约，并用集成测试验证这些边界。

## 五、案例三：AptGuide 2.0 的 Live Eval 纠正了“代码通过等于检索可靠”的误解

### 事实背景

`AptGuide 2.0` 已有较多本地测试通过，但首次将 RAG v2 连接真实 Milvus、embedding 和 lease 环境进行评测时，才暴露出检索和评测数据问题。

### 真实问题

首次 live eval 发现测试集中的文档 ID 与房源 ID 和真实向量数据不一致：

- `KB-APPOINT-*` 与真实 `KB-APPT-*` 不一致；
- `KB-ACCOUNT-*` 与真实 `KB-ACCT-*` 不一致；
- 房源 ID 使用 `3001`、`3002` 等占位符，而非真实数据 ID；
- 部分 query 与期望文档之间的语义映射本身不准。

### 行动与结果

修正评测数据映射后：

| 指标 | 修正前 | 修正后 |
| --- | ---: | ---: |
| KB hit@3 | `14.3%` | `48.6%` |
| KB hit@5 | `14.3%` | `51.4%` |
| Room hit@5 | `0.0%` | `40.0%` |
| 失败案例 | `35` | `20` |

同时，剩余失败被进一步定位到 query understanding、confidence gate 与 room filter，而不是继续把所有问题归因给测试数据。

### 你能讲出的工程认识

> 单元测试和接口跑通只能证明链路能执行，不能证明 RAG 检索质量。评测集本身也需要和线上数据一致，否则得到的指标无法解释。在修正数据映射后，指标提升但仍远未达到目标，反而更清晰地说明了后续应该优化检索而不是继续包装结果。

### 推荐回答版本

> 在 AptGuide 2.0 中，本地测试通过后我进一步跑了接入真实 Milvus、embedding 和 lease 的 live eval。第一次评测的 KB hit@3 只有 14.3%，Room hit@5 是 0。我没有直接去调排序权重，而是先检查评测依据，发现测试集的 KB 文档 ID 命名和房源占位 ID 与真实数据不一致。修正后 KB hit@3 提升到 48.6%，Room hit@5 提升到 40%。  
> 这个结果既说明评测数据对齐很重要，也说明系统当时仍存在真实检索质量问题。因此我更倾向于用 trace 和 failure classification 定位问题，而不是只展示能返回卡片的演示效果。

## 六、案例四：AptGuide 2.0 LLM 结构化输出被系统契约误伤

### 真实问题

在将自然语言理解升级为 LLM-first 后，首次 live eval 出现：

```text
120 个案例中，100 个进入 clarification
```

一开始容易误以为是模型不会理解用户请求，但文档记录的排查结论是：模型实际已经正确生成了 `route`、`rag_task`、`filters` 等语义字段；失败发生在系统验证层。

### 根因

Pydantic `InteractionIntent` 模型要求 `raw_message` 字段，但 `raw_message` 是系统应保留的原始输入元数据，不应该要求 LLM 输出。模型响应缺少该字段时，`model_validate()` 抛出错误，异常处理又统一回退成澄清，从而掩盖了真正原因。

### 修复与结果

修复方式是：解析模型 JSON 后，由系统注入 `raw_message`，再进行 Pydantic 校验。

修复后，澄清案例从：

```text
100/120 -> 15/120
```

剩余问题进一步暴露为检索数据、房源召回和风险校准问题。

### 你能讲出的工程认识

> 这个问题让我认识到，structured output 不等于把完整系统模型都交给 LLM 生成。语义字段属于模型职责，但 trace、原始消息、时间戳等元数据属于系统职责。二者混在一个强校验契约里，很容易产生看似安全、实际难定位的失败。

### 推荐回答版本

> 我印象比较深的一个问题发生在 AptGuide 2.0 做 LLM-first 理解升级时。首次 live eval 中 120 个案例有 100 个被系统要求澄清，看起来像模型几乎无法理解任务。但我检查模型原始输出后发现，模型对路由和筛选条件的理解其实是正确的，真正失败点是 Pydantic 契约要求模型输出一个 `raw_message` 字段，而它本来属于系统侧元数据。验证异常又被安全 fallback 吞掉，所以表现成大量澄清。  
> 后来我把系统元数据改为在解析后注入，再做结构校验，澄清案例下降到 15 个。这个案例让我认识到 LLM 语义输出和系统执行契约必须明确分层，并且安全回退也要保留可观测的失败原因。

## 七、案例五：AptGuide 3.0 房源推荐有结果，但不等于业务可验证

### 真实问题

在 `AptGuide 3.0` 的 live room-search RAG 中，系统能够返回房源卡片，但每张卡片都处于 `vector_only` 状态，无法确认它对应 `lease` 中的真实可预约房源：

```text
lease_validation_requested_count=0
lease_validated_count=0
aptguide3_room_identity_map=0 rows
```

### 根因拆解

文档记录了四类原因：

1. `LeaseClient.validate_rooms()` 将房源 dict 错传给仅处理字符串的 `_to_snake()`，产生异常后被宽泛捕获并返回空列表。
2. 微信房源向量记录只有来源侧 ID，没有 `lease_room_id` 等业务身份映射。
3. 临时整数房源 ID 使用 Python 内置 `hash()` 生成，不同进程可能产生不同结果，影响评测一致性。
4. 已有 `room_index` 中的 ID 与当前 lease 数据也不一致，不能简单切换索引解决问题。

### 已处理与仍保留的边界

已记录的处理：

- 校验客户端使用正确的 dict 字段转换；
- 临时房源 ID 改为确定性 SHA-256 生成；
- 更新评测候选与本地映射 seed。

仍不能夸大的部分：

- 本地 seed 只能服务测试，不是生产身份凭证；
- 在外部房源没有验证映射前，将其标为 `vector_only` 而不是 `lease_validated` 才是正确行为。

### 你能讲出的工程认识

> RAG 返回相关文本或房卡，不代表推荐结果已经可以承担业务动作。对于租房场景，外部线索、向量候选和平台可预约房源是不同层次的数据；推荐前需要完成身份映射和事实源校验，否则不能允许用户直接预约。

### 推荐回答版本

> 在 AptGuide 3.0 的房源推荐评测中，我遇到过一个比召回分数更基础的问题：系统能从向量库返回房源卡片，但这些卡片始终无法通过 lease 业务后端校验。进一步分析发现，一方面外部微信房源只有来源 ID，没有与平台房源的可靠映射；另一方面校验客户端本身还有字典字段转换错误，被异常处理吞掉后表现为空结果。  
> 我修正了客户端转换问题，并把不稳定的临时 ID 改成确定性生成方式。但在数据身份映射没有真正验证之前，我认为系统应该保守地将候选标为外部线索，而不是假装它已经是可预约房源。这个案例让我更明确地理解了 RAG grounding 和业务事实源之间的边界。

## 八、案例六：AptInsight 的评测失败归因与模型配置问题

### 真实问题

`AptInsight` 的 Text-to-SQL 评测中，MiMo 与 Qwen 的总成绩都记录为：

```text
35/40 = 87.5%
安全用例 6/6
边界用例 5/5
```

但两者失败用例集合完全不同，说明总通过率不能解释真实问题。

### 具体问题 A：reasoning 消耗输出预算

MiMo 的 reasoning 输出消耗了 `max_tokens`，导致：

- 意图节点输出为空或 JSON 被截断；
- 本应分析的业务问题被错误路由为 `out_of_scope`；
- 复杂查询 `C01` 中 SQL 节点返回 `null`。

项目记录了对 `reasoning_effort` 与各节点 token 预算的调整，并将通过率从 `50%` 提升至 `87.5%`。

### 具体问题 B：harness failed 不总是系统错

例如浏览趋势问题 `B02`：

- 一种 SQL 使用 `DATE()`；
- 评测规则期待 `DATE_FORMAT()`；
- 两者在该查询场景可以表达等价的按日趋势；
- 因此失败属于 grader 过窄，不应简单算作主链路失败。

另一方面，预约转化率 `C02` 如果没有使用租约数据、误解了指标口径，即便 SQL 能执行，也是真正的业务语义错误。

### 你能讲出的工程认识

> Agent Eval 不是只统计 pass rate。失败需要区分模型节点问题、SQL 业务口径错误、执行错误和评测器误杀；模型选型也不能只看总分，还要看延迟、空响应率以及关键安全用例表现。

### 推荐回答版本

> 在 AptInsight 中，我做 Text-to-SQL 评测时遇到过一个很典型的问题：两个模型总通过率都是 35/40，安全用例也都通过，但失败案例完全不重叠。进一步排查发现，MiMo 在部分节点会因为 reasoning 消耗输出预算而产生空内容或截断 JSON；而另一些失败其实不是系统 SQL 错误，而是 grader 只接受某种 SQL 函数或图表类型。  
> 因此我没有只看一个总体通过率，而是按 intent、SQL 生成、安全守卫、执行和 grader 分层归因。这个过程也让我认识到，Text-to-SQL 的评测既要验证只读安全，也必须验证指标口径，例如预约转化率不能只生成一个可执行但业务定义错误的 SQL。
