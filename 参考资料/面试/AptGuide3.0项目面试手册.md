# AptGuide 3.0 项目面试手册

## 一句话介绍

`AptGuide 3.0` 是面向租客的智能找房助手，以独立 Agent 服务形式验证自然语言找房、租赁规则问答、预约确认、租约查询、偏好记忆和人工转接能力，并计划通过租赁业务网关接回主系统。

## 业务背景

传统租客端页面需要用户手动筛选区域、租金、标签，再分别进入预约或租约页面。AptGuide 希望让用户用自然语言表达需求，例如：

- “我想找番禺 1500 以内、比较安静的房子。”
- “押金不退怎么办？”
- “帮我预约明天下午看房。”
- “查询一下我的租约。”

项目难点不只是生成聊天回答，而是将自然语言交互接入房源、预约和租约等真实业务边界。

## 系统链路

最终集成链路设计如下：

```text
rentHouseH5
  -> lease web-app POST /app/ai/chat
      -> AptGuide 3.0 POST /api/chat
          -> lease internal tools
          -> Milvus
          -> AptGuide Agent state DB / Redis
          -> LLM
```

`lease` 负责鉴权和业务事实；`AptGuide 3.0` 负责对话编排、检索、待确认状态、记忆和可观测信息。前端不直接访问 LLM、向量库或 Agent 内部状态。

## 核心功能

项目将业务交互组织为 7 类 typed procedure：

| Procedure | 解决的问题 | 关键边界 |
| --- | --- | --- |
| `clarify` | 意图不明确、输出低置信度或结构无效 | 不确定时澄清，不强行执行 |
| `room_search` | 自然语言找房与推荐 | 推荐房源需要业务事实校验 |
| `kb_qa` | 押金、退租、维修等规则问答 | 回答尽量基于召回证据，高风险问题谨慎表述 |
| `appointment` | 预约创建/取消/查询 | 写操作需要确认，由 lease 执行最终写入 |
| `lease` | 查询用户自己的租约 | 要求可信用户上下文 |
| `memory` | 保存或读取找房偏好 | 写入记忆需要确认 |
| `handoff` | 需要人工帮助的场景 | 形成受控转接状态 |

## 核心技术方案

### 1. LLM-first 结构化理解

系统让 LLM 根据用户输入输出结构化意图，而不是由关键词直接决定任务、筛选条件或风险姿态。

```text
结构化输出有效且置信度足够 -> 进入对应 procedure
模型不可用、输出无效、低置信度或矛盾 -> clarify
```

面试表达：

> 租客表达方式非常多，例如“预算不要太高”“地铁方便一点”，只靠规则覆盖能力有限，因此理解层采用 LLM-first。但模型的理解结果并不会直接触发执行，而是经过契约校验和确定性流程控制。

### 2. Room Search RAG

找房推荐链路可概括为：

```text
理解用户偏好
-> 构造检索计划与多条查询
-> Milvus 向量召回候选房源
-> 合并与去重
-> 身份映射 / lease 业务校验
-> 偏好评分和排序
-> 返回房源卡片
```

它解决的是用户自然语言与标准房源条件不完全一致的问题。推荐结果不能只来自向量相似度，还要经过业务事实校验，避免把不可用或不可信的候选当作最终推荐。

### 3. KB QA RAG

规则问答链路可概括为：

```text
理解问题和风险等级
-> 知识片段召回与重排
-> 置信度 / 风险门控
-> 基于证据生成回答
-> 返回来源信息
```

押金、退款、提前退租等问题影响用户决策，回答不能无依据承诺。因此这一链路比普通 FAQ 更强调来源与风险控制。

### 4. 确认式写操作

对于预约创建/取消、偏好记忆写入等操作：

```text
LLM 识别意图
-> procedure 生成 pending action
-> 用户明确确认
-> 系统调用 lease 内部工具执行
-> 保存流程与审计状态
```

面试表达：

> Prompt 只能影响模型输出倾向，不能承担业务权限控制。因此模型负责识别“用户想预约”，但只有确定性 workflow 在收到确认后才能调用写接口。

### 5. 状态和可观测性

`AptGuide 3.0` 自己维护 Agent 运行状态，包括 session、message、pending action、memory candidate、handoff、procedure run、trace 与 audit。文档记录了 MySQL 持久化与 Redis TTL 热状态设计，以及 LangSmith 可选追踪和 RAG eval。

## 业务事实与权限边界

| AptGuide 负责 | lease 负责 |
| --- | --- |
| 会话、消息、待确认动作 | 用户身份与正式鉴权 |
| Agent 偏好记忆与候选 | 房源和公寓事实 |
| 人工转接票据、过程 trace | 预约、租约、合同事实 |
| procedure 与审计状态 | 敏感数据与最终业务写入 |

关键表达：

> Agent 是智能编排层，租赁后端仍是业务事实源。集成模式下不能信任前端直接给出的用户身份，而应由 lease 鉴权后向 Agent 注入可信上下文。

## 完成程度与证据

根据项目文档，已实现并记录的能力包括：

- 独立运行的 FastAPI 后端与验证前端；
- 7 类 typed procedure；
- LLM-first 结构化理解；
- Room Search 与 KB QA RAG 管线；
- MySQL / Redis Agent 状态支持；
- 开发模式与内部请求头鉴权边界；
- Playwright E2E、live RAG eval 与诊断追踪探索。

必须同时说明的限制：

- 最终 `rentHouseH5 -> lease -> AptGuide 3.0` 主系统接入在功能列表中标为 deferred；
- live eval 曾暴露房源检索一致性、房源身份映射以及 trace 可见性不足等问题；
- 因此更稳妥的表述是“关键功能开发和验证已完成，主系统集成与稳定性优化仍在推进”，不能说成生产落地完成。

## 真实可讲难点

### 难点一：房源检索质量如何判断

评测早期存在找房案例缺少预期房源 ID 的问题，导致返回了房卡却无法计算检索质量；补充 expected IDs 后，进一步暴露出结果一致性不足。这说明 Agent 评测不能只看“有回答”，还要建立可计算的检索指标与数据映射。

### 难点二：向量数据与业务事实 ID 对齐

来自外部或微信房源数据的标识与 lease 系统中的真实房源 ID 可能不一致。若没有身份映射，检索候选无法可靠调用业务系统校验。可以讲为数据对齐与 grounding 问题，不应夸张为线上事故。

### 难点三：写操作不能依赖模型自律

预约与偏好写入涉及状态变化。项目采用 pending action 与确认流程，把 LLM 能力限制在理解层和生成层，将真正执行交给确定性代码与业务后端。

## 2 分钟项目介绍参考答案

> AptGuide 3.0 是我围绕公寓租赁场景开发的租客侧智能找房助手。它希望解决用户在找房时筛选条件表达灵活、规则咨询分散，以及预约和租约服务入口割裂的问题。用户可以直接用自然语言找房、咨询押金或退租规则，也可以发起预约、查询自己的租约和保存偏好。
>
> 架构上，它作为独立 Agent 服务开发验证，最终链路计划由租客 H5 经过 lease 业务网关调用 AptGuide。这样 `lease` 继续作为房源、预约、租约与用户身份的事实源，Agent 负责会话、检索、待确认动作和响应编排。
>
> 技术方案上，理解层采用 LLM-first 的结构化输出；找房场景采用多查询向量召回、候选校验和排序的 Room Search RAG；规则咨询采用带来源与风险门控的 KB QA RAG。对于预约或偏好写入等操作，模型只识别意图，系统生成待确认动作，用户确认后才调用后端工具执行。
>
> 这个项目让我比较深入地认识到 AI 应用的关键不是只把模型接进来，而是让模型在业务事实、权限、安全和评测约束下工作。目前项目完成了独立服务与关键能力验证，并做过 live eval 和诊断分析；完整主系统集成及检索稳定性优化仍属于继续推进的部分。

## 面试官追问题

1. 为什么坚持 LLM-first，不使用关键词兜底？遇到模型服务不可用怎么办？
2. 找房 RAG 与规则问答 RAG 的检索、排序和可靠性目标有什么不同？
3. pending action 如何防止重复确认、过期执行或用户身份错配？
4. 推荐房源为什么还需要 lease 校验，向量库返回结果不够吗？
5. 检索结果不稳定时，你如何建立数据集并定位问题属于理解、召回还是排序？
6. 如果要将系统真正接入 H5，你认为还需要补哪些工程工作？
