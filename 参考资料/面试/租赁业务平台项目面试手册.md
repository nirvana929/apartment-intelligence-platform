# 租赁业务平台项目面试手册

## 平台定位

`apartment-intelligence-platform` 是围绕公寓租赁业务构建的一体化工程，包含业务后端、管理后台、租客 H5，以及租客侧和运营侧两个 AI Agent。

它的面试价值在于说明：`AptGuide 3.0` 和 `AptInsight` 并非脱离业务的数据演示，而是围绕房源、预约、租约、运营分析等实际业务实体进行的 AI 应用探索。

## 子系统关系

| 子系统 | 用户 | 主要职责 |
| --- | --- | --- |
| `lease/web-admin` | 管理员 / 运营 | 后台 API：公寓、房间、属性、预约、租约、用户、岗位 |
| `lease/web-app` | 租客 / H5 / AI 工具 | 登录、找房、预约、租约、浏览历史、AI 网关与内部工具 |
| `rentHouseAdmin` | 管理员 / 运营 | Vue3 管理后台，承载运营管理界面 |
| `rentHouseH5` | 租客 | Vue3 移动端入口，承载找房与租客服务页面 |
| `AptGuide 3.0` | 租客 | 智能找房、规则问答、确认式交互 |
| `AptInsight` | 管理员 / 运营 | 安全只读的智能经营分析 |

## 平台边界设计

平台最重要的架构观点是：

> 业务系统作为事实源，AI Agent 作为智能编排层，前端通过业务网关使用 AI 能力。

租客链路：

```text
租客
  -> rentHouseH5 / AI 助手入口
  -> lease web-app /app/ai/chat
  -> AptGuide 3.0
      -> lease internal tools
      -> Milvus / LLM / Agent state
```

运营链路：

```text
管理员
  -> rentHouseAdmin / 智能运营分析入口
  -> lease web-admin /admin/ai/chat
  -> AptInsight
      -> SQL Guard
      -> MySQL 只读查询
      -> 表格 / 图表 / 总结
```

## lease 后端可讲内容

`lease` 采用 Spring Boot 3 + Java 17 + Maven 多模块架构：

```text
lease/
├── common/          JWT、Redis、MinIO、验证码、Web 基础能力
├── model/           实体、枚举与基础模型
└── web/
    ├── web-admin/   管理后台服务
    └── web-app/     租客服务及 AI 内部工具入口
```

`web-app` 已文档化的租客业务 API 包括：

- 短信登录与当前用户信息；
- 房源列表与房间/公寓详情；
- 预约创建或更新、我的预约；
- 我的租约与状态更新；
- 浏览历史、地区、租期和付款方式；
- `/app/ai/chat` AI 对话转发入口。

文档还记录了 `/internal/ai/tools/*` 工具接口，用于 AI 服务访问房源搜索、数据同步、预约创建与列表、租约查询等业务能力，并通过内部 token 和用户标识限定调用上下文。

## 两个前端可讲内容

### rentHouseH5

租客端使用 Vue3、Vite、TypeScript、Vant 与 Pinia。面试重点不必讲模板能力，而应聚焦于其在平台中的角色：

- 展示房源列表与详情；
- 支持预约、租约、浏览记录等租客流程；
- 作为 AptGuide 最终交互入口，通过业务网关发起 AI 对话。

### rentHouseAdmin

管理后台使用 Vue3、Vite、TypeScript、Element Plus、Pinia 和 ECharts，适合高频表格、筛选和管理流程。面试中可将它描述为：

- 承载公寓、房源、预约、租约、用户和岗位管理；
- 作为 AptInsight 后续集成的运营分析 UI 入口；
- 由 Spring Boot 负责鉴权与后端转发，避免前端直接访问 AI 服务或数据库。

## 平台设计取舍

### 为什么 AI 不直接连接前端

前端直接访问 Agent 会绕开用户鉴权、内部 token、统一错误处理和业务审计。通过 `lease` 网关转发，业务服务可以控制可信身份和工具权限。

### 为什么 Agent 不持有最终业务事实

房源可预约状态、租约、合同和用户敏感数据已经属于租赁业务域。若 Agent 复制维护一份最终事实，会产生一致性与权限风险。Agent 可以保存会话和待确认状态，但业务结果应由 `lease` 提供。

### AptGuide 与 AptInsight 为什么分别设计

两类用户、风险和数据操作不同：

- 租客助手需要交互、推荐与有限的确认式业务操作；
- 运营分析助手需要数据库分析，但边界应严格限制为只读。

将它们拆开能使权限、安全策略和评测目标更清晰。

## 面试介绍参考答案

> 我的项目不是只有一个独立的聊天 Demo，而是围绕公寓租赁业务搭建的平台。底层 `lease` 后端负责房源、预约、租约与身份等业务事实，租客端和管理端分别通过 H5 与后台界面使用系统能力。在这个基础上，我探索了两个 Agent：租客侧的 AptGuide 3.0 用来找房、问答和受控预约，运营侧的 AptInsight 用来进行只读经营分析。
>
> 我比较关注它们和业务系统之间的边界。前端不会直接调用模型或数据库，而是经过 Spring Boot 网关；AI 服务负责理解与编排，业务事实和最终操作仍由后端管理。这样既能利用自然语言交互，也能保留已有业务系统的鉴权、一致性和安全控制。

## 可追问题

1. 为什么不将两个 Agent 合成一个统一助手？
2. `lease web-app` 在 AptGuide 集成中解决了哪些安全问题？
3. 如果 Agent 推荐的房源已下架，系统应如何处理？
4. 租客查询自己的租约和管理员做经营分析，在权限模型上有什么差异？
5. Spring Boot 与 Python Agent 之间如何设计错误码、超时和追踪字段？
