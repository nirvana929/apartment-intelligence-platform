# STAR 案例库

## 使用方式

本文件提供面试训练素材。每个案例都应基于项目文档可支撑的事实来讲。若实际参与细节、个人动作或结果指标需要进一步确认，应在面试训练前回查源码、提交记录或评测报告，不要把建议措辞当作未经核实的个人经历。

回答顺序：

```text
Situation 背景 -> Task 任务 -> Action 行动 -> Result 结果 -> Reflection 反思
```

## 案例一：AptGuide 的写操作安全边界

**适用问题：** 你在项目中如何考虑风险？为什么不能完全依赖大模型？

**S - 背景**

AptGuide 不只回答问题，还涉及预约创建/取消和偏好记忆写入。此类操作会改变业务或用户状态。

**T - 任务**

在保留自然语言交互体验的同时，避免 LLM 因误判或不稳定生成直接触发写操作。

**A - 行动**

- 将 LLM 职责限制为意图识别和响应生成；
- 将业务交互拆为 typed procedure；
- 对预约和记忆写入引入 `pending action`；
- 要求用户确认后，由确定性流程调用 `lease` 内部业务工具执行；
- 保持业务事实由 `lease` 持有，Agent 只维护交互过程状态。

**R - 结果**

项目文档记录了确认式 procedure 与待确认状态设计，实现了写操作不直接由模型自由执行的系统边界。

**反思表达**

> 这不是我遇到过线上误操作之后才补的补丁，而是开发验证阶段主动考虑的风险控制。它让我认识到 Prompt 是软约束，真正影响业务数据的行为需要由后端流程约束。

## 案例二：AptGuide RAG 评测暴露检索问题

**适用问题：** 你遇到过什么真实技术问题？如何判断 Agent 效果？

**S - 背景**

AptGuide 的 Room Search RAG 可以返回房源卡片，但早期评测数据缺少预期房源 ID，导致很难量化推荐质量。

**T - 任务**

建立能区分“有返回结果”和“召回结果正确”的评测依据，并进一步定位检索链路问题。

**A - 行动**

- 在评测数据中补充 expected room IDs；
- 增加房源身份映射相关存储与导入/导出支持；
- 重新运行 live RAG gate，观察 Hit@K 与 failure owner；
- 将问题从数据集缺口进一步定位为向量召回/语义查询一致性问题。

**R - 结果**

文档记录中，数据集缺口被识别并补足后，房源搜索仍出现 `Hit@5=False` 的案例，从而明确下一步优化方向不是“补一个页面”，而是检索一致性和身份映射。

**反思表达**

> 对 Agent 系统来说，演示时能返回内容并不足够。尤其是推荐场景，需要有 ground truth、身份对齐和检索指标，否则很容易误以为系统已经可靠。

## 案例三：AptInsight 的 Text-to-SQL 安全控制

**适用问题：** 你如何设计可控的 AI 数据分析？如何处理隐私和数据库安全？

**S - 背景**

AptInsight 让运营人员以自然语言查询业务数据库。如果直接执行模型生成的 SQL，可能访问敏感字段或造成写入风险。

**T - 任务**

在支持灵活经营查询的同时，确保查询是只读、安全、符合数据权限边界的。

**A - 行动**

- 将产品能力限定为运营只读分析，不提供业务写操作；
- 使用 `sqlglot` 做 AST 级 SQL Guard；
- 仅允许 `SELECT`，拦截多语句、系统库、非白名单表与敏感字段；
- 使用只读 MySQL 账号作为第二道防线；
- 使用安全用例和边界用例进入 Eval Harness。

**R - 结果**

项目 README 记录的基线中，安全测试 `6/6` 通过，边界情况 `5/5` 通过；总体评测为 `35/40`。

**反思表达**

> 评测结果说明安全边界在当前用例上可验证，但业务分析仍有改进空间。因此我不会把离线测试说成生产安全保证，而是把它作为持续回归的基础。

## 案例四：指标口径与系统能力边界

**适用问题：** 你如何避免模型胡编业务结论？需求无法支持时怎么办？

**S - 背景**

运营人员可能询问“真实收入”或“某个房间的预约转化”等问题，但当前数据结构未必包含支付流水或足够的预约维度。

**T - 任务**

让系统基于已有数据回答可以回答的问题，对缺失数据的问题明确拒答或说明限制。

**A - 行动**

- 整理 schema 和指标口径作为 SQL 生成上下文；
- 明确合同租金不等价于已收收入；
- 明确预约表缺失房间字段时不能宣称房间维度预约分析；
- 对不支持的问题返回限制说明，而不是生成看似合理的 SQL 或结论。

**R - 结果**

该边界被写入 AptInsight 总体设计与安全范围，成为面试中体现业务理解和数据严谨性的例子。

**反思表达**

> Text-to-SQL 的可靠性不仅是 SQL 能运行，更要保证问题本身在数据层可回答，且指标定义没有被模型偷换。

## 案例五：使用 AI Coding 组织多模块开发

**适用问题：** 你怎样使用 AI 工具？如何证明项目是你掌控的？

**S - 背景**

平台涉及 Python Agent、Spring Boot 业务系统、Vue 前端、检索、评测与文档，模块较多。

**T - 任务**

利用 AI Coding 提高开发和整理效率，同时保持架构边界、安全规则与验证过程一致。

**A - 行动**

- 先拆清项目角色：业务事实源、Agent 状态、网关与前端入口；
- 用文档明确关键约束，例如 AptGuide 的确认流程、AptInsight 的只读边界；
- 使用工具辅助实现、检索、文档和测试工作；
- 通过测试/评测记录发现并承认仍存在的失败，例如检索稳定性与业务分析通过率未满。

**R - 结果**

形成了具备文档、测试和评测依据的多项目材料，并能明确哪些能力完成、哪些尚需继续集成优化。

**反思表达**

> AI Coding 提高了局部实现效率，但也让我更加重视契约、一致性与验收。面试中我愿意基于真实文档和代码说明自己理解和负责的内容。

## 训练要求

- 回答前先在心里组织“观点、原因、例子、方案”。
- 被追问个人职责时，只说明自己确实能解释或核实的部分。
- 提到结果时附带来源限定，例如“项目评测文档记录为……”，避免把离线指标表述成线上效果。
