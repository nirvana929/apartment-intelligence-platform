# AI Coding 面试表达手册

## 目标

在项目开发中使用 Codex、Claude Code 等 AI Coding 工具并不是需要回避的事情。面试关键是证明：工具提升了实现效率，而需求理解、系统设计、风险判断与验收仍由你负责。

## 推荐定位

> 我把 AI Coding 看作工程协作工具。它擅长辅助生成局部实现、测试脚手架、文档和代码检索结果，但我会先明确需求与模块边界，并对关键业务逻辑、安全约束、调试验证和最终交付负责。

## 不推荐说法

| 不推荐表达 | 风险 |
| --- | --- |
| “这个项目基本都是 AI 写的。” | 面试官会怀疑你是否理解实现与排错过程 |
| “我会很多 AI 工具，所以开发能力强。” | 工具列表不能证明工程判断 |
| “模型生成出来能运行就可以。” | 暴露缺少测试、安全和维护意识 |
| “AI 帮我解决了所有 Bug。” | 很容易被追问真实定位过程而失真 |

## 可以真实展开的工作方式

### 1. 需求拆解

你可以说：

> 在让 AI 辅助实现之前，我会先明确这个需求属于哪个模块、依赖哪些业务事实、可能引入什么风险。例如预约操作涉及写入，因此无论代码如何生成，都必须保留确认流程和业务网关边界。

### 2. 架构和契约约束

项目中适合用来支撑这一观点的例子：

- AptGuide 将 Agent 状态与 lease 业务事实分开；
- AptGuide 的写操作使用 pending action 与确认流程；
- AptInsight 只允许只读 SQL，并设置 SQL Guard；
- 两个 Agent 都通过文档、测试或 eval 来校验结果。

### 3. 代码审查与验证

你可以说：

> AI 生成的局部代码需要结合上下游接口和已有规则检查。我会重点检查状态命名是否一致、API 字段是否契约匹配、危险操作是否绕过安全边界，并通过测试或评测确认变更效果。

## 为什么 AI Coding 仍然需要工程能力

### 命名和状态一致性

多个版本迭代中，AI 可能分别生成含义接近却不一致的状态或函数，导致模块之间协同出错。开发者需要维护统一契约。

### 多文件影响范围

一个功能往往涉及后端接口、前端类型、数据库 schema、配置、测试和文档。AI 可以修改其中一部分，但开发者必须检查整体链路。

### 安全边界不会自动保持

即使 prompt 里说明“写操作要确认”，后续生成代码仍可能无意间引入直接调用写接口的路径。关键限制要落实在确定性代码、权限和测试中。

### 评测比一次成功更重要

Agent 或 Text-to-SQL 系统的表现会受 prompt、数据、schema 和模型影响。不能只凭一次演示判断正确，需要 eval 数据集和失败分析。

## 面试问题与参考回答

### Q：你的项目是不是主要靠 AI 工具完成的？

> 我确实使用了 AI Coding 工具提升开发效率，例如辅助梳理文档、生成局部实现和测试框架。但项目中最关键的判断仍由我负责：比如 AptGuide 中业务事实和 Agent 状态的边界、写操作确认流程，以及 AptInsight 中只读 SQL 和 AST 校验边界。这些不是让模型自由生成就能可靠决定的。我也需要阅读实现、定位失败、运行测试和整理评测结果，确保生成内容符合系统目标。

### Q：使用 AI Coding 时你遇到过什么风险？

> 我比较关注长期迭代的一致性风险。Agent 项目涉及意图结构、状态、API 契约和评测数据，局部代码即使能运行，也可能和其他模块不一致。因此我会把关键边界写入文档和测试，并通过评测结果检查修改是否让行为发生漂移。

### Q：既然 AI 能写代码，开发者价值在哪里？

> 我认为局部代码生成成本确实在下降，但真实业务开发仍然需要定义正确问题、划分系统边界、判断风险、组织数据与评测，以及对结果负责。在我的项目里，模型能帮助实现代码，但不能替我决定预约是否可以直接执行，也不能替我保证 SQL 不访问敏感数据。

## 与项目结合的表达素材

| 项目事实 | 可体现的 AI Coding 工程意识 |
| --- | --- |
| AptGuide 有 7 类 procedure | 通过明确流程边界减少生成代码随意扩张 |
| 写操作需要确认 | 将安全规则落在代码流程，而非仅依赖 prompt |
| AptGuide 有 live RAG eval 问题分析 | 用评测发现“返回房卡”不等于检索正确 |
| AptInsight 有 SQL Guard 与安全测试 | 用确定性校验约束模型生成结果 |
| AptInsight 评测基线并非 100% | 承认限制并定位后续优化方向 |

## 表达底线

- 不需要主动贬低 AI 工具，也不要把工具使用隐藏起来。
- 不把 AI 生成过程等同于个人已经掌握所有细节；准备好解释关键模块。
- 被问到未亲手深入定位的实现细节时，可以坦诚说明，并回到自己理解和验证过的边界。
