# AptInsight 项目面试手册

## 一句话介绍

`AptInsight` 是面向公寓运营人员的智能分析助手，将管理员的自然语言经营问题转换为经过安全校验的只读 SQL，并输出表格、图表和中文业务总结。

## 业务背景

传统后台适合固定列表和固定筛选，但运营人员常需要临时回答跨表或趋势问题，例如：

- 本月各公寓预约量排名如何？
- 当前租约状态分布怎样？
- 哪个区域平均租金更高？
- 哪些房源浏览量较高但没有有效签约？

为每个问题开发一个固定报表成本高，因此项目探索用 Text-to-SQL 支持灵活分析，同时将风险限制在只读范围内。

## 当前阶段

项目文档将 AptInsight 当前定位为第一阶段独立验证服务：

```text
调试入口 / API 请求
  -> FastAPI AptInsight Agent
      -> LLM + Schema / 指标上下文
      -> SQL Guard
      -> MySQL 只读查询
      -> 表格 / 图表 / 总结
```

第二阶段设想为：

```text
rentHouseAdmin
  -> lease web-admin /admin/ai/chat
      -> AptInsight
```

因此面试中可以讲 MVP 与验证能力，不能将管理后台完整集成说成已交付生产功能。

## 能力范围

| 能力 | 说明 |
| --- | --- |
| 自然语言经营分析 | 预约、租约、房源、租金、浏览热度和基础经营诊断 |
| LangGraph 工作流 | 规范化、意图分类、上下文选择、SQL 生成、安全检查、执行、图表与总结 |
| SQL Guard | 使用 `sqlglot` 做 AST 级安全校验 |
| 只读执行 | 独立只读 MySQL 访问，控制风险 |
| 结果表达 | 返回行列、图表配置、中文总结、错误与 `trace_id` |
| Eval Harness | 回归 SQL 准确性、安全场景、边界场景和业务分析问题 |

## 工作流讲法

```text
用户问题
-> 问题规范化与意图判断
-> 选择相关 schema / 指标口径
-> LLM 生成 SQL
-> sqlglot AST SQL Guard
-> 只读 MySQL 执行
-> 构造表格 / ECharts 图表
-> 生成业务总结
```

系统还应区分两类无需正常查询的输入：

- 指标解释问题：直接说明口径，不为了“显得智能”强行查库。
- 数据库不支持或越权问题：明确拒答或说明缺少字段，不编造结果。

## 安全设计重点

### 1. 不信任模型生成 SQL

模型能够生成 SQL，并不意味着 SQL 可以直接执行。项目使用 `sqlglot` 将 SQL 解析为 AST 后进行检查，包括：

- 只允许 `SELECT`；
- 拦截多语句；
- 约束白名单业务表与字段；
- 拦截敏感字段和系统库访问；
- 配合只读数据库账号执行。

### 2. 不做写操作

项目明确不提供 `INSERT`、`UPDATE`、`DELETE` 或 DDL 能力。与 AptGuide 的“确认后允许特定写操作”不同，AptInsight 的产品边界就是只读运营分析。

### 3. 不编造业务指标

例如系统没有账单或支付流水时，只能分析合同约定租金规模，不能将其表述为真实收款收入；预约表缺乏房间字段时，也不能声称具备房间维度预约分析能力。

## 已记录的验证结果

根据 `AptInsight/README.md`，当前文档记录的基线为：

| 指标 | 结果 |
| --- | --- |
| 总评测通过率 | `35/40`，即 `87.5%` |
| 安全测试 | `6/6`，`100%` |
| 边界情况 | `5/5`，`100%` |
| 业务分析 | `24/29`，`82.8%` |
| 单元测试 | 文档记录 `22` 个通过 |
| Ruff | 文档记录 `0` 错误 |

面试表述要加限定语：“根据项目当前评测基线记录”。不要将离线评测成绩说成生产准确率。

## 与 AptGuide 的区别

| 对比点 | AptGuide 3.0 | AptInsight |
| --- | --- | --- |
| 用户 | 租客 | 运营/管理员 |
| 主要任务 | 找房、问答、预约、租约交互 | 经营数据分析 |
| 核心智能链路 | RAG + typed procedures | Text-to-SQL + SQL Guard |
| 写操作策略 | 特定操作确认后由业务后端执行 | 永远不执行业务写操作 |
| 可靠性重点 | 房源真实性、问答证据、确认状态 | SQL 安全、指标口径、只读权限 |

## 2 分钟项目介绍参考答案

> AptInsight 是我面向公寓后台运营场景做的智能分析助手。传统后台可以维护房源和租约，但运营人员如果临时想分析预约趋势、租金分布或房源经营状况，通常需要导出数据或者新增报表接口。这个项目希望让管理员通过自然语言直接查询业务数据。
>
> 第一阶段我将它设计为独立的 FastAPI Agent 服务：系统先识别问题并选择相关 schema 和指标上下文，再让模型生成 SQL；SQL 不会直接执行，而是先经过基于 sqlglot 的 AST 安全校验，只允许访问白名单业务数据的 SELECT，再使用只读 MySQL 账号执行。结果会以表格、图表和中文总结返回。
>
> 我在这个项目中重点关注 Text-to-SQL 的可控性。一方面要让模型正确理解指标口径，例如合同租金不能直接等于真实收入；另一方面要防止危险 SQL 或敏感数据访问。因此我设置了只读边界和评测集。项目文档记录的当前评测基线是 40 个案例中通过 35 个，其中安全用例 6 个全部通过。
>
> 当前它属于独立 MVP 验证阶段，后台集成和生产部署仍是后续工作。这让我认识到 AI 数据分析系统不只看 SQL 能不能生成，更重要的是安全校验、指标口径和可回归评测。

## 面试官追问题

1. AST 级校验相比字符串禁止关键字有什么优势？
2. 如何防止模型访问身份证号、手机号或后台权限表？
3. 如果 SQL 语法错误，系统是否允许修复重试？如何防止无限循环？
4. 为什么不把数据库所有 schema 一次性全放进 prompt？
5. 评测中的 5 个失败案例主要属于什么问题，下一步会怎么提升？
6. 如何区分“合同月租金”与“真实已收收入”？
