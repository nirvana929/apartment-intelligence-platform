## 2. 当前最重要的面试表达原则

### 2.1 不要硬编经历

不要说：

我线上遇到过模型绕过 confirmation，直接删除租约。

如果没有真实发生过，就不要说。否则面试官可能会继续追问：

* 怎么发现的？
* 日志怎么看？
* 当时链路怎么追踪？
* workflow 状态怎么修？
* tool permission 怎么做？
* 有哪些回归测试？

这些问题如果没有真实经验，就很容易答不上来。

---

### 2.2 可以说“设计阶段主动考虑过”

正确表达应该是：

这个具体线上事故我目前没有遇到过，因为项目还在开发和验证阶段。但在设计写操作流程时，我主动考虑过类似风险。我的理解是，大模型更适合做语义理解和意图识别，但不应该直接拥有数据库写权限。因此在创建租约、取消预约这类写操作里，我设计上会倾向于加入用户确认流程，由系统 workflow 控制真正执行。

这比硬编 bug 更可信，也更体现工程意识。

---

### 2.3 用“真实经历 + 理论理解 + 设计取舍”回答

回答项目问题时，可以按这个结构：

1. 真实做过什么。
2. 在开发中遇到什么问题。
3. 这个问题背后的工程本质是什么。
4. 自己是怎么理解和改进的。
5. 目前哪些只是设计阶段考虑，还没有完全生产化。

字节并不只是看技术栈，而是看候选人是否具备真实团队开发能力，包括：

* 能不能讲清楚项目。

## 5. 面试回答的万能结构

我当前最大问题是“想到什么说什么”，容易发散。建议所有系统设计类问题都使用四段式：

观点 → 原因 → 例子 → 方案

也可以记成：

观因例解

---

### 5.1 观：先给核心观点

例如面试官问：

为什么不能完全依赖 Prompt？

先回答：

因为 Prompt 本质上只是 soft constraint，不能作为真正的系统执行约束。

---

### 5.2 因：解释为什么

继续说：

LLM 本质上是 probabilistic token generation，它会根据当前上下文生成最像合理的输出，但不会像传统程序一样严格执行规则。

---

### 5.3 例：举例

例如：

比如删除租约这种写操作，如果上下文里同时有“快速操作”“自动化”“提升用户体验”等目标，仅靠 prompt 可能让模型倾向于直接执行，而不是稳定地进入用户确认流程。

注意：如果这个例子不是项目真实事故，要说明是设计阶段的风险推演，不要说成线上 bug。

---

### 5.4 解：解决方案

最后说：

所以我的设计思路是让 LLM 负责意图识别，真正数据库写操作必须经过 confirmation workflow，由后端受控接口执行。

## 7. AI Coding 为什么“生成代码不是最难的”

这是我需要重点理解和表达的内容。

---

### 7.1 核心观点

现在的大模型已经非常擅长局部代码生成，但 AI Coding 真正困难的不是一次生成能不能跑，而是系统在长期迭代过程中是否还能保持一致、可验证、可维护。

---

### 7.2 为什么说它不稳定

这里的“不稳定”不是指：

每次生成都跑不起来。

而是指：

系统长期演化的一致性无法天然保证。

---

### 7.3 具体体现

#### 1. 命名漂移

例如系统里本来使用：

pending / confirmed / canceled

后续 AI 生成代码时可能使用：

waiting / success / cancelled

当前文件可能能跑，但其他模块依赖旧状态，系统就会出现隐性错误。

---

#### 2. 状态漂移

例如预约流程原本是：

created → confirmed → canceled

后来某次迭代中 AI 为了实现支付功能，可能变成：

created → paid → confirmed

单个功能看似合理，但 payment、refund、notification、analytics 等模块可能都受影响。

---

#### 3. 业务规则漂移

例如系统原则是：

所有写操作必须二次确认。

后续某次为了“提升用户体验”或“快速操作”，AI 可能生成直接执行的逻辑，绕过 confirmation。

---

#### 4. 多文件协同遗漏

AI 修改一个文件时，可能忘记同步：

* config
* migration
* schema
* frontend type
* test
* API contract
* prompt
* documentation

这就是多文件协同中的全局一致性问题。

---

#### 5. 重复逻辑

AI 很容易复制已有逻辑，生成多个功能相近但命名不同的函数，例如：

validate_booking()

check_booking()

verify_booking()

长期会导致系统越来越乱。

---

## 8. LLM 的能力边界

---

### 8.1 核心观点

LLM 的能力来源于大规模统计模式学习，它非常擅长局部模式生成，但软件工程需要长期一致性、系统因果关系、隐含业务约束和全局架构演化。这些不是单纯 token pattern 能完全解决的问题。

---

### 8.2 主要边界

#### 1. 长期状态维护弱

LLM 没有真正 persistent memory。上下文长了会丢，项目大了会漂，多文件协同容易忘。

---

#### 2. 系统级一致性弱

LLM 不会天然永远遵守同一套架构原则。Prompt 中写了规则，只能提高它遵守规则的概率，不能保证 100%。

---

#### 3. 隐含规则理解弱

很多业务规则没有明确写在文档里，但人类默认知道。

例子：

用户说：

我要查一下 302 房间那个女生的信息。

人类知道这是隐私越权，应该拒绝。但如果系统没有显式规则，模型可能只把它当成普通查询请求。

再如：

用户说：

帮我退押金。

人类知道这是资金操作，风险高。模型可能只把它当成客服请求。

---

#### 4. 真实世界 grounding 不足

模型不真正承担现实后果。它没有真正的业务责任、法律责任、资金风险意识。

---

#### 5. 全局优化能力弱

它擅长当前步骤最优，不擅长长期架构演化最优。

---

## 9. Prompt 为什么只是 soft constraint

---

### 9.1 核心观点

Prompt 不是 compiler，也不是 rule engine。它不能提供硬约束，只能提高模型按某种方式输出的概率。

---

### 9.2 举例

Prompt 里写：

所有删除操作必须确认。

这会让模型更倾向于遵守，但不能保证它永远不会违反。

真正硬约束应该是：

if not confirmed:

reject()

这才是 hard constraint。

---

### 9.3 面试表达

可以这样讲：

我理解 Prompt 更像 soft constraint，它可以影响模型输出倾向，但不是严格执行机制。因此对创建租约、取消预约、删除数据这类写操作，不能只依赖 prompt，而应该在系统层加 workflow、权限控制和 confirmation。

---

## 10. Pure Agent、Agentic Workflow 和 Workflow 的区别

---

### 10.1 Pure Agent

Pure Agent 通常指：

用户输入 → LLM 自主规划 → 自主调用工具 → 自主决定执行 → 自主结束

特点是自治程度高，但不可控风险也高。

适合：

* 问答
* 总结
* 文案
* research
* 代码草稿
* 低风险探索性任务

不适合：

* 资金
* 合同
* 医疗
* 隐私
* 删除数据
* 修改权限
* 企业核心流程

---

### 10.2 Workflow

Workflow 是程序员显式编排流程，模型只在固定节点内工作。

例如：

Query Understanding → Retrieval → Validation → Response

它更稳定，但灵活性比 Agent 低。

---

### 10.3 Agentic Workflow

Agentic Workflow 是更适合工业落地的中间形态：

LLM 参与理解、推理和生成，但系统通过 workflow、policy、tool permission 和 state machine 控制执行边界。

可以表达为：

现代工业系统并不是否定 Agent，而是在重新定义 Agent 的自治边界。低风险场景可以更自治，高风险场景必须受系统约束。

---

## 11. ReAct 和因果理解的区别

---

### 11.1 ReAct 是什么

ReAct = Reason + Act

模型会：

Thought → Action → Observation → Thought → Answer

它让模型在推理过程中调用工具，根据工具结果继续回答。

---

### 11.2 ReAct 不等于真正因果理解

ReAct 的 Thought 本质仍然是 token sequence generation。它只是把推理步骤显式展开，让模型更容易完成多步任务。

真正因果理解要求模型理解：

操作 → 状态变化 → 后果影响

例如：

取消预约 → 房源释放 → 支付可能退款 → 通知用户 → 财务记录变化

ReAct 可能写出看似合理的推理链：

用户想快速取消预约，所以我应该直接取消。

但它不一定天然理解：

取消预约是写操作，必须进入 confirmation workflow。

---

### 11.3 面试表达

ReAct 提升的是模型多步任务能力和工具调用能力，但它并不能替代系统级约束。真正的因果和风险控制仍然需要 workflow、state machine 和 tool permission 负责。

---

## 13. 可讲的真实踩坑方向

我可以重点准备以下真实方向。

---

### 13.1 自然语言和数据库 schema 不一致

问题：

用户说的是自然语言，但数据库字段和值有固定格式。

例如：

* 用户说“天河区”，数据库里可能存的是标准行政区名称或编码。
* 用户说“一房一厅”，系统内部可能需要映射成 canonical room type。
* 用户说“便宜一点”，系统需要映射成预算范围或排序偏好。

解决思路：

* normalization
* canonical mapping
* query understanding
* structured output
* schema linking

面试表达：

我发现直接让模型基于用户自然语言生成查询并不稳定，因为用户表达和数据库 schema 不一定一致。因此我增加了归一化处理，把用户表达先映射成系统内部可识别的 canonical value，再进入检索或 SQL 生成流程。

---

### 13.2 RAG 检索不稳定

问题：

用户表达和知识库文档表达不一致，导致召回不稳定。

解决思路：

* query rewrite
* multi-query retrieval
* rerank
* source validation
* answer grounded in retrieved context

---

### 13.3 Text-to-SQL 安全问题

问题：

自然语言转 SQL 不能直接执行，需要校验。

解决思路：

* 只允许 SELECT。
* 用 sqlglot 做 AST 级 SQL Guard。
* 禁止 DROP / DELETE / UPDATE / INSERT。
* 白名单表字段。
* 执行前检查 limit。
* 查询结果再总结。

---

### 13.4 AI Coding 长期迭代混乱

问题：

开发多个版本后，代码会出现重复逻辑、命名不一致、模块边界模糊。

解决思路：

* 自己先拆需求。
* 生成计划。
* 明确模块边界。
* 每次开发后 review。
* 对关键逻辑加测试。
* 文档记录核心约束。

---

## 14. STAR 案例准备方向

---

### 14.1 案例一：自然语言到数据库查询的归一化问题

S：在开发 AptGuide / AptInsight 时，用户自然语言和系统内部字段不一致。

T：需要让用户自然语言稳定映射到数据库查询或检索条件。

A：通过结构化理解、字段归一化、canonical mapping，使模型输出更接近系统可执行格式。

R：提高了查询稳定性，也让我意识到 LLM 不能直接对接复杂业务系统，中间需要 schema linking 和规范化层。

---

### 14.2 案例二：Text-to-SQL 安全校验

S：AptInsight 需要让管理员用自然语言查询数据库。

T：既要能生成 SQL，又要保证不能执行危险 SQL。

A：设计 SQL 生成后加入 AST 校验，只允许只读查询，限制表和字段，拒绝危险操作。

R：使系统能够在保留自然语言交互能力的同时，降低数据库风险。

---

### 14.3 案例三：AI Coding 协作开发

S：项目功能较多，涉及后端、AI 服务、检索、测试和前端联调。

T：需要提高开发效率，同时保证自己理解和控制系统。

A：使用 AI Coding 工具生成计划和代码，但自己负责需求拆解、模块设计、代码 review、调试和验收。

R：提高了开发速度，也让我意识到 AI Coding 最难的不是生成代码，而是长期一致性和可维护性。

## 15. 面试官可能追问及回答方向

---

### Q1：你为什么认为不能完全依赖 LLM？

回答方向：

因为 LLM 本质是概率生成模型，它擅长语义理解和局部推理，但不是严格的规则执行器。对于写数据库、退款、删除等高风险操作，必须用系统层 hard constraint 控制。

---

### Q2：把规则写进 Prompt 不就行了吗？

回答方向：

Prompt 只能作为 soft constraint，提高模型遵守规则的概率，但不能作为真正的执行权限控制。真正的控制应该在 workflow、权限、状态机和 tool layer 中实现。

---

### Q3：Pure Agent 是否没有价值？

回答方向：

不是。Pure Agent 在低风险、探索性任务中很有价值，比如 research、文档总结、代码草稿。但在资金、合同、隐私、数据库写操作等高风险场景，不能让它完全自治，需要 bounded autonomy，也就是 agentic workflow。

---

### Q4：你自己项目到底做到什么程度？

回答方向：

我目前项目还处在开发和验证阶段，并没有完全 productionize。但我在开发过程中已经做了 Query Understanding、RAG、Text-to-SQL、SQL Guard、AI Coding 协作开发等探索，也开始主动思考 workflow、structured output、confirmation、eval 等工程化方向。

---

### Q5：你遇到过最真实的问题是什么？

回答方向：

不要说没遇到过。可以讲：

* 自然语言与数据库 schema 不一致。
* SQL 生成需要安全校验。
* RAG 召回不稳定。
* AI Coding 多版本迭代后命名和逻辑漂移。
* 多轮对话上下文组织困难。

---

## 16. 当前需要避免的表达

---

### 16.1 避免说“我做了完整生产级系统”

除非真的上线并有用户量、日志、告警、回归测试、灰度和监控，否则不要这么说。

---

### 16.2 避免说“AI 帮我写完了项目”

这会让面试官怀疑工程能力。

---

### 16.3 避免大量堆黑话

比如连续说：

* Agent
* Workflow
* Guardrail
* Harness
* Policy
* State Machine

但讲不出具体例子，会显得虚。

---

### 16.4 避免说“这个我没做过”后停住

应该改成：

这个具体生产事故我没有遇到过，但我在设计阶段主动考虑过类似风险。实际开发中，我遇到的是另一个相关问题……

---

## 17. 更适合我的总体表达策略

最适合我的面试策略是：

不假装自己已经是工业级专家，而是表现出真实项目经验、快速学习能力、工程 sense 和对 AI 系统边界的深刻思考。

可以反复强调：

1. 我做过真实项目，不只是看概念。
2. 我用了 AI Coding，但我负责需求拆解、设计、review 和验收。
3. 我知道 LLM 有边界，不会把它当万能工具。
4. 我已经开始从 Demo 思维转向 AI Engineering 思维。
5. 我希望在实习中把这些能力进一步落到真实业务系统中。

---

## 18. 后续训练建议

后续 Agent 应继续帮助我做以下训练：

1. 按照“观因例解”训练每个面试问题。
2. 针对 AptGuide 准备 3 个真实踩坑案例。
3. 针对 AptInsight 准备 3 个真实踩坑案例。
4. 准备 3 分钟自我介绍。
5. 准备 1 分钟简短自我介绍。
6. 准备 STAR 案例：困难克服、解决问题、团队协作、学习能力。
7. 准备 AI Coding 如何讲得高级且不踩雷。
8. 准备算法笔试表达和常见手撕题。
9. 对“没做过但理解过”的内容，统一用“设计阶段考虑 / 理论理解 / 后续优化方向”表达，不要伪装成已上线成果。
10. 每次回答都要求我先停顿 2 秒，在心里组织：观点、原因、例子、方案。

---

## 19. 最重要的一句话

我的核心面试形象应该是：

一个具备后端工程基础、真实做过 AI 应用项目、会使用 AI Coding 提升效率，并且已经开始理解 LLM 边界、系统约束和 AI Engineering 的成长型工程师。

不要包装成：

已经做过完整生产级 Agent 平台的专家。

前者真实且有潜力；后者容易被追问击穿。
