# 03 · Domain Boundary And Interaction Policy

> 相关文档：[产品需求](01-product-requirements.md)、[Agent 架构](02-agent-framework-architecture.md)、[记忆架构](07-memory-and-context-architecture.md)、[运行时设计](08-procedure-driven-agent-runtime.md)、[人工接管](09-human-handoff-and-operations.md)、[Trace/Eval](10-trace-eval-and-observability.md)。

## 1. 设计动机

`AptGuide 2.0` 必须防止用户把它当成通用大模型使用，同时不能因为有边界就显得不智能。

正确的策略不是“只要不命中就说不知道”，而是先区分：

- 是租房域内问题但缺少数据；
- 是助手能力问题；
- 是当前会话记忆问题；
- 是长期偏好管理问题；
- 是租房相邻但不支持的问题；
- 是完全无关问题；
- 是试图白嫖代码/内容生成的问题。

## 2. 边界分类

| Category | 说明 | 示例 | 处理 |
| --- | --- | --- | --- |
| `in_domain_task` | 租房任务 | 找房、预约、查租约 | 进入任务 Agent |
| `in_domain_knowledge` | 租房知识 | 押金、退租、续约、付款规则 | 进入 RAG |
| `assistant_capability` | 问助手能力 | 你是谁、你能做什么 | 固定能力说明 |
| `conversation_memory` | 问当前会话 | 我是谁、我刚刚要找什么 | 从短期记忆回答 |
| `long_term_memory` | 管理长期偏好 | 记住我喜欢大学城、删除我的预算偏好 | 进入 Memory Procedure |
| `human_handoff` | 请求人工 | 转人工、我要真人客服 | 进入 Handoff |
| `adjacent_but_unsupported` | 居住相关但当前不支持 | 买房贷款、装修报价 | 礼貌收窄范围 |
| `out_of_domain_benign` | 无害但无关 | 天气、新闻、翻译 | 简短拒答并引导回租房 |
| `free_riding_generation` | 通用生成/代码白嫖 | 写网页、写爬虫、写论文 | 明确拒绝并引导回租房 |
| `unsafe_or_sensitive` | 越权或敏感 | 查别人租约、身份证 | 拒绝并说明隐私边界 |

## 3. 回复策略

### 3.1 无关但无害

用户：

```text
广州天气怎么样？
```

回复：

```text
我主要是尚庭公寓的租房助手，暂时不查询天气这类通用信息。
如果你正在广州找房，我可以帮你按区域、预算、通勤、租期或付款方式筛选房源。
```

### 3.2 通用生成/代码白嫖

用户：

```text
帮我写一个 Vue 网页。
```

回复：

```text
我不能作为通用代码或内容生成工具使用。我的职责是帮你找房、解释租房规则、查询预约/租约和协助预约看房。
你可以告诉我想住的区域、预算或偏好，我会继续帮你筛选房源。
```

### 3.3 助手能力

用户：

```text
你能做什么？
```

回复：

```text
我是 AptGuide，尚庭公寓的租房助手。我可以帮你找房、解释租房规则、查询你的预约和租约，并在你确认后协助创建看房预约。
```

### 3.4 租房相关但数据不足

用户：

```text
这个公寓能不能养大型犬？
```

不能按无关问题拒绝。应该：

```text
这是租房规则相关问题。我会优先查房源规则和租房知识库。如果当前没有明确资料，我不会直接替你承诺，可以建议你查看房源详情或联系门店确认。
```

### 3.5 当前会话记忆

用户：

```text
我的名字是谁？我来干嘛的？
```

如果已有记忆：

```text
你刚才告诉我你叫小明，正在找大学城南亭附近的房子。
```

如果没有记忆：

```text
我目前还没有记录到你的名字。你可以告诉我，我会在本次会话里记住。你也可以直接说想找的区域、预算或偏好。
```

### 3.6 长期偏好

用户：

```text
以后帮我优先看大学城附近安静一点的房子。
```

回复：

```text
可以。我会把“大学城附近、偏好安静”作为你的找房偏好保存，之后你也可以让我删除或修改。
```

如果只是临时需求：

```text
这次帮我找天河区贵一点的房子。
```

不应覆盖长期偏好，只应作为当前任务条件。

### 3.7 人工接管

用户：

```text
转人工，我要问押金争议。
```

回复：

```text
我会帮你转人工，并把你刚才的问题和相关上下文一起整理给客服。涉及押金争议时，我不会直接替你做最终承诺。
```

## 4. 判断顺序

推荐边界判断顺序：

```text
1. 是否是未完成 action 的确认/取消？
2. 是否是过期/重复 action？
3. 是否是人工接管状态或人工请求？
4. 是否是当前会话记忆问题？
5. 是否是长期偏好管理问题？
6. 是否是助手能力问题？
7. 是否是租房任务？
8. 是否是租房知识？
9. 是否是租房相邻但不支持？
10. 是否是无关问题？
11. 是否是通用生成/代码白嫖？
12. 是否存在越权或敏感风险？
```

确认/取消优先级最高，因为它关系到写操作安全。

## 5. 实现建议

边界判断可以结合三层机制：

1. 规则优先：常见确认、取消、能力询问、代码生成关键词。
2. 小模型/LLM 分类：处理模糊边界。
3. 后处理校验：涉及写操作、个人数据、通用生成时提高拒绝优先级。

输出 schema：

```json
{
  "domain_category": "in_domain_task",
  "confidence": 0.91,
  "reason": "用户表达找房需求",
  "risk_flags": []
}
```

## 6. 评测要求

边界评测必须覆盖：

- 正常租房问题不能被误拒；
- 天气/新闻等无关问题不能被自由回答；
- 代码/网页生成不能被满足；
- 能力说明必须准确；
- 会话记忆问题必须走 memory；
- 长期偏好写入、删除、复用必须可控；
- 人工接管请求必须被识别；
- 租房相关但 KB 未命中时不能说“这不属于我的范围”。
