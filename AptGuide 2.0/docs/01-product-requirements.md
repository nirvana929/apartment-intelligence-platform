# 01 · Product Requirements

> 相关文档：[Start Here](00-start-here.md)、[领域边界策略](03-domain-boundary-and-interaction-policy.md)、[前端交互协议](05-frontend-interaction-protocol.md)、[记忆架构](07-memory-and-context-architecture.md)、[人工接管](09-human-handoff-and-operations.md)、[产品技术评审](13-product-technical-review.md)。

## 1. 产品定位

`AptGuide 2.0` 是尚庭公寓租客侧的智能找房 Agent。它不是通用聊天机器人，也不是简单客服 FAQ，而是围绕租房任务提供对话、推荐、规则问答、预约协助和个人租约/预约查询的交互式应用。

产品必须同时满足两个目标：

- **租房域内更智能**：能理解模糊需求、记住短期上下文、复用长期偏好、主动恢复失败、解释推荐逻辑。
- **租房域外更克制**：对天气、写代码、写论文、通用内容生成等无关请求不调用通用模型能力，明确引导回租房服务。

## 2. 用户场景

### 2.1 找房

用户可以用自然语言提出需求：

```text
我想租大学城南亭附近的房子，预算 1500 左右。
预算我都接受，主要想离大学城近一点。
帮我找天河区 3000 以内、能月付的房子。
想找安静一点、适合考研的房间。
```

系统应该做到：

- 抽取预算、区域、地标、通勤、付款方式、租期、偏好标签；
- 区分 hard filter 和 soft preference；
- 对地标/商圈/学校等非标准区域做归一化；
- 检索为空时自动放宽条件并解释；
- 返回房源卡片、推荐理由和可操作按钮。

### 2.2 租房规则问答

用户可以询问：

```text
押金怎么退？
提前退租怎么处理？
预约看房要注意什么？
能不能养宠物？
```

系统应该先判断是否属于租房知识域。属于租房域时，即使知识库没有命中，也不能简单按“无关问题”拒绝，而应该说明当前没有可靠规则来源，并建议查看房源详情或联系门店。

### 2.3 看房预约

用户可以从推荐卡片发起预约，也可以自然语言表达：

```text
帮我预约第一个，明天下午三点。
预约天河创客空间 1008，2026-05-06 14:00。
```

预约是写操作，必须遵循：

- 参数完整；
- 房源标识可信；
- 有 `confirmation_id`；
- 用户明确确认；
- 后端执行成功后清理 pending action；
- 旧确认按钮不能触发新操作。

### 2.4 我的预约和租约

用户可以查询：

```text
我现在有几个预约？
我的租约什么时候到期？
```

系统通过用户身份调用受控工具接口，不能让前端直接传入可信 user_id，也不能暴露其他用户数据。

### 2.5 助手能力与会话记忆

用户可以问：

```text
你是谁？
你能做什么？
我的名字是谁？
我刚刚来干嘛的？
```

系统应当从能力配置和短期记忆中回答，而不是落入通用 fallback。

### 2.6 长期偏好记忆

用户可以表达长期偏好：

```text
以后主要帮我看大学城附近的房子。
我一般预算两千以内，最好能月付。
我考研，比较在意安静。
```

系统应该做到：

- 区分“本次需求”和“长期偏好”；
- 对长期偏好生成 memory candidate；
- 在用户确认后写入长期画像；
- 用户下次回来时可加载相关偏好；
- 用户可以查看、修改和删除长期偏好；
- 不保存身份证、电话、合同编号等敏感信息。

### 2.7 人工接管

用户可以要求人工：

```text
转人工。
我要找真人客服。
这个押金问题我要投诉。
```

系统应该做到：

- 识别人工接管请求；
- 工具连续失败、高风险争议或用户情绪明显负面时主动建议人工；
- 生成给人工客服的上下文摘要；
- 人工接管后暂停 AI 自动回复；
- 人工处理完成后可恢复 AI。

## 3. 关键能力

| 能力 | 说明 | MVP |
| --- | --- | --- |
| 独立前端 | 浏览器聊天、卡片、操作按钮、确认卡片 | 是 |
| Agent API | 后端对话接口、流式事件、结构化响应 | 是 |
| 领域边界 | 防止通用问答/代码生成白嫖 | 是 |
| 短期记忆 | 保存用户主动提供的名字、目标和偏好 | 是 |
| 长期画像 | 保存用户确认过的稳定租房偏好 | 是 |
| 上下文压缩 | 长对话中保留摘要和结构化状态 | 是 |
| 任务阶段 | 区分收集需求、展示结果、等待确认、工具失败等阶段 | 是 |
| 找房 Agent | 区域归一、渐进式检索、推荐解释 | 是 |
| 规则 RAG | 租房规则问答和来源引用 | 是 |
| 预约 Workflow | 强确认、过期处理、防重复提交 | 是 |
| 人工接管 | 高风险或失败场景转人工并带上下文 | 是 |
| Trace | 记录可审计执行轨迹，不暴露原始思维链 | 是 |
| 工具注册表 | 真实 lease / vector 工具统一 schema | 是 |
| Eval Harness | 对话质量、边界、安全、检索恢复评测 | 是 |

### 3.1 MVP 分层说明

上表中的 “MVP=是” 表示第一版需要有最小契约或最小可演示能力，不表示一次性做完整产品形态。

第一版必须完整跑通：

- 独立前端聊天；
- Agent API；
- 领域边界；
- 短期记忆和任务阶段；
- Tool Registry；
- 真实房源搜索；
- 预约 confirmation workflow；
- Trace；
- 核心 eval。

第一版可以做基础能力、后续再增强：

- 长期画像：先做 candidate + 用户确认 + 删除，不做复杂自动提升；
- 上下文压缩：先保证结构化 state 不丢，摘要可简单；
- 人工接管：先做主动转人工、失败转人工和摘要，不做完整工单系统；
- 运营分析：先记录 trace 和知识缺口日志，不做完整后台。

## 4. 成功标准

第一版成功标准：

- 用户可以在独立前端基于真实后端数据完成找房、追问、推荐、预约确认的完整演示；
- 对无关天气/代码生成问题能说明边界，而不是直接生成答案；
- 对“我是小明，我来找大学城南亭附近的房子”能记住短期事实；
- 对用户确认过的长期偏好能在新会话中复用，但不会擅自执行写操作；
- 对“预算不限/预算我都接受”能清除旧预算约束；
- 对空检索能尝试放宽，并解释为什么没有精确匹配；
- 旧确认按钮点击后不会执行任何写操作；
- 工具连续失败或合同/押金争议能转人工并提供上下文摘要；
- trace 能复盘每次边界判断、工具调用、恢复和确认动作；
- 所有房源、租约、预约数据都来自真实 `lease` 接口或受控知识库，不由模型编造。

## 5. 范围边界

明确支持：

- 找房推荐；
- 房源筛选；
- 租房规则问答；
- 看房预约协助；
- 我的预约/租约查询；
- AptGuide 能力说明；
- 当前会话内的非敏感记忆问答。
- 用户确认过的长期租房偏好记忆；
- 人工接管和上下文摘要；

明确不支持：

- 通用代码生成；
- 通用网页生成；
- 论文/文案代写；
- 天气、新闻、股票等通用实时信息；
- 法律意见；
- 绕过业务系统直接查库；
- 未确认的写操作；
- 自动保存敏感个人信息；
- 替人工客服裁定合同、押金、赔偿争议。
