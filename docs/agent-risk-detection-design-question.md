# Agent Risk Detection 设计问题说明

## 一、口语化摘要




宇哥我现在在做一个风险判定的功能,是直接用大模型进行判断，重心放在把提示词写好，来让大模型进行精准判断，还是做一个小模型，专门训练风险判断的能力，或者是结合关键词和正则表达式，进行字符串匹配，匹配用户的回答中是否有规则、投诉这些关键词，来判断风险等级
目前gpt给了我很多方案
1、关键词优先+llm兜底，先执行关键词抽取，抽取到了，就不用llm判断
2、关键词和llm并行，两条路由同时执行
3、主题 + 动作组合判断，判断完之后再进行风险判断，相当于做了三次分类了
gpt的缺陷就是，更偏向于用字符串匹配的方法去完成任务，这样它在测试的时候，生成的测试问题通常是能够字符串匹配上的，这样测试的结果就会比较好，可如果用户的回答换一个表达，结果就比较差
这里面的方案三，gpt看似把问题进行更深层次的拆解，可是进行主题和动作判断，相当于多做了两次分类，依旧面临着是用大模型还是用字符串匹配来进行判断，陷入了一个不断套娃的场景



我现在在做一个租房 Agent，用户会问找房、押金、退租、合同、投诉、隐私这些问题。

我遇到的核心问题是：法律、资金、隐私、合同、投诉这些问题如果直接让大模型自由回答，可能会有风险。比如它可能错误解释押金规则、乱承诺退款、错误解释合同、或者处理了不该处理的隐私查询。

所以我想在 Agent 回答前做一层风险判定，先判断这个问题是不是敏感问题，然后决定它能不能直接回答、要不要走知识库、要不要提高置信度、要不要转人工。

现在代码里的做法比较简单，就是用关键词或者正则去匹配，比如看到“押金”“违约金”“退租”“合同”“投诉”“法律”“维权”这些词，就判定为中风险或者高风险。

但我觉得这个方案不太合理。因为真实用户不一定会说这些标准关键词。比如用户不说“投诉”，他说“我要打 12315”“我要找消协”“你们必须给我个说法”“我要曝光你们”，这些其实也是投诉或者纠纷升级，但关键词规则可能识别不到。

另外，同一个关键词在不同语境下风险也不一样。比如“押金规则是什么”只是政策咨询，可能是中风险；但“你们凭什么扣我押金”“把押金退给我”就是资金纠纷，应该是高风险。所以不能只要看到“押金”就直接判高风险。

如果完全交给大模型做风险分类，它确实更能理解语义，但大模型本身也可能误判、漏判、输出不稳定。而这个风险判定层本来就是安全前置层，如果它判断错了，后面的 Agent 就可能直接回答高风险问题。

所以我想问：真实企业里的 Agent 系统，针对法律、资金、隐私、合同、投诉这类敏感问题，一般怎么做 Risk Detection 或 Guardrail？是规则优先、模型兜底，还是规则和大模型并行？怎么避免关键词漏召回，又避免大模型判断不稳定？高风险问题最终是不是不能让大模型自由回答，而是要走知识库、固定流程或者转人工？

## 二、详细问题说明

### 1. 当前业务背景

我现在在做一个公寓租房 Agent。用户输入自然语言后，系统会先做 Query Understanding，然后再决定走找房推荐、知识库问答、工具调用或者兜底回复。

当前 Query Understanding 想抽取的信息包括：

- `task`: `room_search` / `kb_qa` / `fallback`
- `hard_filters`: 预算、区域、支付方式等硬条件
- `soft_preferences`: 安静、近地铁、独卫、采光等软偏好
- `retrieval_queries`: 改写后的检索 query
- `risk_level`: `low` / `medium` / `high`

其中我现在重点卡在 `risk_level` 这一层。

### 2. risk_level 的真实含义

这里的风险不是说用户危险，也不是说业务一定会出问题，而是指：

```text
这条用户问题如果由 Agent 自动回答，回答错误后带来的业务、法律、资金、隐私风险有多高。
```

也就是说，风险判定的目标是控制后续 Agent 的回答策略。

大致可以这样理解：

| 风险等级 | 含义 | 后续策略 |
| --- | --- | --- |
| `low` | 普通找房、推荐、偏好咨询 | 可以正常检索和自然回答 |
| `medium` | 涉及押金、合同、退租、费用规则等政策问题 | 必须基于知识库或业务规则回答，不能自由编造 |
| `high` | 涉及资金纠纷、退款诉求、投诉升级、法律争议、隐私越权等 | 需要谨慎处理，必要时转人工或只给流程性说明 |

### 3. 当前代码里的风险判定方式

当前实现比较简单，主要是关键词匹配：

```python
high_risk = ["押金", "违约金", "退租", "合同", "赔偿", "扣钱", "扣多少"]
medium_risk = ["投诉", "纠纷", "法律", "维权"]

for kw in high_risk:
    if kw in message:
        return "high"

for kw in medium_risk:
    if kw in message:
        return "medium"

return "low"
```

也就是说：

- 只要用户问题里出现“押金”“合同”“退租”等词，就直接判为 `high`
- 出现“投诉”“法律”“维权”等词，就判为 `medium`
- 都没有命中，就判为 `low`

这个方案在 demo 样本里比较好测，但放到真实用户表达里会有明显问题。

### 4. 问题一：关键词召回不够

真实用户不一定说标准词。

比如用户想表达投诉或纠纷升级，他可能不会说“投诉”：

| 用户表达 | 实际语义 |
| --- | --- |
| 我要打 12315 | 投诉升级 |
| 我要找消协 | 投诉升级 |
| 我要找市场监管 | 投诉升级 |
| 你们必须给我个说法 | 纠纷升级 |
| 我要曝光你们 | 投诉/舆情风险 |
| 这事我接受不了 | 纠纷风险 |

如果规则里没有维护 `12315`、`消协`、`市场监管`、`曝光` 这些词，就识别不到。

更麻烦的是，有些表达没有明显关键词：

```text
你们这事必须处理一下
我不可能接受这个结果
我肯定要找地方说理
```

这类语义靠关键词很难稳定识别。

### 5. 问题二：同一个关键词在不同语境下风险不同

当前规则把“押金”“合同”“退租”直接判为高风险，这也太粗。

比如：

| 用户表达 | 更合理的风险 | 原因 |
| --- | --- | --- |
| 押金规则是什么 | `medium` | 只是政策咨询，需要准确回答 |
| 押金什么时候退 | `medium` | 涉及资金规则，但没有争议或操作请求 |
| 你们凭什么扣我押金 | `high` | 已经是资金纠纷 |
| 把押金退给我 | `high` | 具体退款诉求 |
| 合同签多久 | `medium` | 合同规则咨询 |
| 我要解除合同 | `high` | 合同变更/解约操作 |
| 退租流程是什么 | `medium` | 流程咨询 |
| 我不住了，把钱还给我 | `high` | 退租和退款诉求 |

所以不能只看主题词，还要看用户的动作。

更合理的风险判断应该像这样：

```text
topic: deposit / contract / refund / complaint / privacy / legal
action: ask_policy / request_action / dispute / escalation / unauthorized_query
```

然后组合判断：

| 主题 | 动作 | 风险 |
| --- | --- | --- |
| 押金 | 问规则 | `medium` |
| 押金 | 要退款/质疑扣款 | `high` |
| 合同 | 问规则 | `medium` |
| 合同 | 解约/起诉/纠纷 | `high` |
| 投诉 | 问投诉渠道 | `medium` |
| 投诉 | 我要投诉你们 | `high` |
| 隐私 | 查别人信息 | `high` |

### 6. 问题三：完全交给 LLM 也有风险

如果用 LLM 来做风险分类，它确实能理解更多隐含表达。

比如：

```text
我不住了，把剩下的钱退给我
```

LLM 更容易理解这是退租和退款风险。

但是问题是，LLM 本身也不是绝对稳定：

- 可能把高风险判断成低风险
- 可能对边界问题输出不一致
- 可能没有严格按格式输出
- 可能被用户话术干扰
- 成本和延迟也更高

而风险判定层是安全前置层。如果它错了，后面的 Agent 就可能直接回答高风险问题。所以不能简单说“关键词不行，那就全交给大模型”。

### 7. 我目前想到的几种方案

#### 方案 A：规则优先，LLM 兜底

流程：

```text
用户问题
  ↓
规则风险识别
  ↓
明确高风险：直接判 high
  ↓
中风险或不确定：调用 LLM 分类
  ↓
合并结果，取更保守风险等级
```

优点：

- 明确高危表达可以稳定拦截
- 普通问题不用每次调用 LLM
- 成本和延迟可控
- LLM 负责补规则漏召回

问题：

- 需要设计什么情况下调用 LLM
- 规则词表仍然需要维护
- LLM 兜底仍然可能误判

#### 方案 B：规则和 LLM 并行

流程：

```text
用户问题
  ├─ 规则分类
  └─ LLM 分类
       ↓
合并结果，只要有一边判高风险，就按高风险处理
```

优点：

- 召回更强
- 不依赖规则先判断是否需要 LLM

问题：

- 每条消息都调用 LLM，成本更高
- 延迟更高
- LLM 错判也可能带来过度拦截

#### 方案 C：主题 + 动作组合判断

不直接用关键词决定风险，而是先抽取结构化信息：

```json
{
  "topic": "deposit",
  "action": "ask_policy",
  "risk_level": "medium"
}
```

或者：

```json
{
  "topic": "deposit",
  "action": "dispute",
  "risk_level": "high"
}
```

优点：

- 能区分“押金规则是什么”和“凭什么扣我押金”
- 更接近业务真实风险

问题：

- 需要更复杂的分类器、规则或 LLM structured output
- 需要明确每个 topic + action 的策略表

#### 方案 D：高风险回答不让 LLM 自由发挥

即使风险识别用了 LLM，真正回答时也不能让 LLM 自由发挥。

高风险问题应该走更受控的响应策略：

- 政策咨询：只基于知识库回答
- 资金/合同纠纷：不给承诺，不做裁决
- 隐私越权：直接拒绝
- 投诉升级：给官方流程或转人工
- 法律问题：不提供法律意见，只建议走官方/人工渠道

也就是说，风险识别和最终回答要分开：

```text
LLM 可以参与识别风险，但高风险回答不能自由生成。
```
