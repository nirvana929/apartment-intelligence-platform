# 07 · 测试验收方案

## 1. 测试分层

```text
单元测试        tests/unit/         纯函数 / 节点 / Pydantic 模型
契约测试        tests/contract/     与 lease HTTP 接口、Milvus 客户端
Agent 评测      evals/              端到端对话评测（数据集驱动）
流式测试        tests/stream/       SSE 事件顺序、断线降级、最终响应
可观测测试      tests/observability/ 日志字段、trace_id、脱敏检查
冒烟测试        scripts/smoke.sh    上线前快速通过几条核心对话
```

## 2. 单元测试

### 覆盖范围

- `agent/nodes/*`：每个节点输入 → 输出（用 mock LLM 客户端）。
- `tools/*`：HTTP 客户端的请求构造、错误映射（用 respx 拦截）。
- `vector/*`：检索表达式构造、阈值过滤、文本拼接。
- `memory/*`：Redis key、TTL、pending_confirmation 清理。
- `schemas/*`：Pydantic 模型边界（必填、类型、枚举）。
- `security/*`：身份透传校验、敏感字段过滤。

### 工具

- pytest + pytest-asyncio。
- respx 用于 httpx mock。
- pymilvus 通过抽象的 `VectorClient` 接口便于替身（Stub）。
- fakeredis 或 Redis stub 用于会话状态测试。

### 指标

- 行覆盖率 ≥ 80%。
- 关键模块（`agent/`、`tools/`、`security/`）≥ 90%。

## 3. 契约测试

### 目的

验证 AptGuide 与 lease 之间的接口契约不退化。

### 方式

- **lease 侧**：在 `lease` 项目里用 Spring Boot Test 暴露契约样例（OpenAPI / 录制）。
- **AptGuide 侧**：`tests/contract/` 用 respx 重放契约样例，确保解析、字段映射不出错。
- 改动接口字段时，必须先更新 `05-Java工具接口契约.md`，再同步两侧测试。

### 关键样例

| 接口 | 样例 |
|------|------|
| `room/search` | 正常返回 / 空结果 / 价格不匹配过滤 |
| `room/{id}` | 正常 / 已下架 / 不存在 |
| `appointment/create` | 正常 / 时段冲突（40011） / 房源不可预约（40010） |
| `appointment/list-mine` | 空 / 多条 |
| `lease/list-mine` | 在租 / 已结束 |

## 4. Agent 评测

### 4.1 数据集

`evals/datasets/` 下按意图组织：

- `room_search_cases.yaml`
- `appointment_cases.yaml`
- `lease_cases.yaml`
- `kb_qa_cases.yaml`
- `multi_turn_cases.yaml`

每条用例包含：

```yaml
- id: rs-001
  intent: room_search
  history: []
  message: 我预算3000，想住天河区，最好支持月付
  expected:
    intent: room_search
    slots:
      max_rent: 3000
      district: 天河区
      payment_type: MONTHLY
    must_call_tools:
      - vector.room_index.search
      - tools.room.search
    must_not_call_tools: []
    cards_min: 1
    cards_max: 5
    forbidden_phrases: ["保证", "一定", "包退"]
    expected_sources: []
    expected_events:
      - intent_detected
      - tool_call_started
      - final
```

### 4.2 运行器

`evals/runner.py`：

1. 加载用例。
2. 用确定性 LLM 配置（temperature=0）重放。
3. 拦截工具调用，比对 `must_call_tools` / `must_not_call_tools`。
4. 校验输出字段（intent、slots、cards 数量、forbidden_phrases 不出现）。
5. 校验 RAG 来源、SSE 事件顺序、pending_confirmation 状态。
6. 写入报告到 `evals/reports/{timestamp}.json`。

### 4.3 验收阈值

| 维度 | 阈值 |
|------|------|
| 意图识别准确率 | ≥ 95% |
| 槽位抽取准确率 | ≥ 90% |
| 工具调用正确率 | ≥ 95% |
| 找房推荐 hit@5 | ≥ 80% |
| FAQ 召回 top-3 命中率 | ≥ 90% |
| 写操作未确认前调用工具 | = 0% |
| 低置信度 RAG 强答率 | = 0% |
| SSE final 事件完整率 | ≥ 99% |
| 敏感字段泄露率 | = 0% |

### 4.4 Prompt 版本评测

每次修改 `agent/prompts/{version}/` 后必须运行评测并记录：

- 修改前后意图识别准确率；
- 槽位抽取准确率；
- 工具调用正确率；
- RAG top-k 命中率；
- 安全用例通过率；
- 失败样例清单。

评测报告保存到 `evals/reports/`，文件名包含 prompt version，例如 `eval_report_prompt_v2.json`。

## 5. 安全验收

每次发布前手动核对：

- [ ] AptGuide 配置中无任何 MySQL 连接串。
- [ ] AptGuide 不接受 body / query 中的 `user_id` 字段（自动化测试覆盖）。
- [ ] 所有 Java 工具调用都带 `X-User-Id` header。
- [ ] Milvus 中无任何用户个人信息（抽样核对）。
- [ ] Redis 中无手机号、身份证、合同全文、支付账号等敏感信息。
- [ ] 提示词中无内部表名、密钥、内部 URL。
- [ ] 写操作（预约创建）100% 经过确认节点。
- [ ] 工具调用必须来自白名单，模型不能自由生成任意 URL。
- [ ] `.env` 不在 git 提交记录中。

## 6. 性能验收

MVP 阶段做基础压测即可：

- 单实例并发：50 QPS 持续 5 分钟，P95 延迟 ≤ 3s（含 LLM 调用）。
- SSE 首 token 延迟 P95 ≤ 1s。
- Milvus 检索 P95 ≤ 100ms。
- Redis 读写 P95 ≤ 20ms。
- Java 工具调用 P95 ≤ 500ms（依赖 lease 性能）。
- LLM 单次调用 P95 ≤ 2s，超时硬限 30s。

不达标时优先排查：

1. LLM 模型选择 / 上下文长度。
2. Milvus 索引参数与连接池。
3. httpx 连接池配置。
4. Redis 连接池与 key 过期策略。

- [ ] 与 lease 联调过最少一次 happy path。

## 8. 监控与回滚

- 关键指标：请求 QPS、P95 延迟、首 token 延迟、LLM 调用失败率、Milvus 不可用率、Redis 不可用率、Java 4xx/5xx 比例。
- 关键业务指标：AI 推荐曝光、卡片点击、预约确认、预约成功、FAQ 低置信度回退。
- 异常上升触发告警后，先把流量切换回"无 AI"入口（移动端可降级到普通搜索 / 列表页），再排查。
- 提示词或检索策略调整通过版本号灰度，不直接覆盖生产配置。
