# 01 · 助手总体设计

## 1. 项目定位

**AptGuide** 是 `apartment-intelligence-platform` 中面向 **租客（C 端）用户** 的智能助手服务。项目采用两阶段交付：

1. **独立应用阶段**：先实现一个可独立运行、带聊天界面的 AptGuide 应用，便于本地演示、调试 Agent 能力和沉淀评测集。
2. **系统集成阶段**：再把 AptGuide 接入现有 `rentHouseH5`、`lease` 和 `AptInsight` 所在的业务系统，形成 C 端找房助手与 B 端运营分析助手的数据闭环。

最终集成形态下，AptGuide 嵌入到 `rentHouseH5` 移动端，作为对话入口，帮助用户：

- 用自然语言找房并获得推荐；
- 在助手内完成看房预约；
- 查询自己的预约和租约；
- 咨询租房规则、流程、FAQ。

AptGuide 与同仓库 `AptInsight`（运营 / 管理员端，Text-to-SQL）互为补充，但**完全独立部署、独立鉴权、独立数据访问路径**。两者不互相调用，通过 `lease` 业务系统和 MySQL 数据沉淀形成闭环：AptGuide 产生找房、预约等 C 端行为，AptInsight 分析这些行为的经营效果，运营再调整房源、标签和规则知识库。

## 2. 设计目标

1. **降低用户找房门槛**：用户用自然语言表达需求即可获得推荐，不必逐项设置筛选器。
2. **承接模糊偏好**："安静一点"、"适合考研"、"通勤方便"——通过 Milvus 语义检索召回。
3. **统一咨询入口**：把"找房 / 预约 / 租约 / FAQ"四类问题收敛到同一个聊天窗口。
4. **可控可审计**：所有真实业务数据访问通过 Java 后端工具接口，便于权限、脱敏、审计统一管理。
5. **可独立演示再集成**：第一阶段先让 AptGuide 作为独立聊天应用可用，第二阶段再接入现有 H5、Java 后端和后台分析链路，降低联调风险。

## 3. 非目标（MVP 不做）

- 不做 IM 客服转人工。
- 不做支付、缴费、合同签署。
- 不做经营分析、运营报表（这是 AptInsight 的职责）。
- 不做语音交互、图像识别（后续迭代再考虑）。
- 不做跨用户的房源对比 / 拼房 / 社交。

## 4. 用户与场景

### 4.1 主要用户

- **意向租客**：尚未签约，正在挑选房源。
- **在租租客**：已签约，需要查询租约、续约、退租、报修咨询。

### 4.2 典型场景

| 场景 | 用户输入 | 期望结果 |
|------|----------|----------|
| 显式条件找房 | "我预算 3000，想住天河区，最好支持月付" | 返回 3~5 个房源卡片 + 推荐理由 |
| 模糊偏好找房 | "想找安静一点、适合考研、通勤方便的房子" | 追问预算/区域 → 语义召回 → 房源卡片 |
| 多轮补全 | "帮我推荐一个房子" | Agent 主动追问关键条件 |
| 看房预约 | "帮我预约第一个房源明天下午看房" | 摘要确认 → 调用预约接口 → 反馈结果 |
| 个人租约查询 | "我的租约什么时候到期？" | 仅返回当前用户租约 |
| 规则咨询 | "提前退租会扣押金吗？" | RAG 检索退租规则后回答 |
| 浏览历史推荐 | "根据我最近看过的房子推荐类似的" | 调 Java 取浏览历史 → Milvus 找相似 |

## 5. 范围边界

### 5.1 系统边界

第一阶段系统边界：

```text
[ AptGuide Web UI ] ← 本地 / 演示入口
       ↓ HTTP
[ AptGuide (FastAPI + LangGraph) ]
   ├─ Milvus（向量库）
   ├─ Mock / Stub 工具数据
   └─ 可选 lease 内部接口（具备联调条件后启用）
```

第一阶段目标是验证产品体验、Agent 工作流、RAG 召回、工具调用协议、写操作确认和评测体系。它允许用 Mock 数据完成端到端演示，但接口结构必须按第二阶段真实集成设计。

第二阶段系统边界：

```text
[ rentHouseH5 ]  ← 用户态
       ↓ JWT
[ lease (Java) ] ← 业务、权限、数据库
       ↓ 内部 token + userId
[ AptGuide (Python) ] ← 对话、检索、推荐理由
   ├─ Redis（会话状态 / 待确认操作）
   ├─ Milvus（向量库）
   └─ HTTP 调用 lease 内部接口
```

AptGuide 的工作仅限于：**理解意图 → 抽取槽位 → 调度工具 → 组织回答**。

它**不做**：直接 SQL 查询、用户登录鉴权、消息推送、文件存储、支付、合同管理。

### 5.2 数据边界

- **可读**：Milvus（公开数据）、Redis 会话状态（仅限当前 `session_id`）、Java 工具接口返回的数据（已按用户身份过滤）。
- **不可读**：MySQL（任何表）、MinIO、Java 内部模型对象、其他用户或其他会话的 Redis 数据。
- **可写**：通过 Java 写接口（创建预约等），且必须经过用户确认。
- **可写**：Redis 会话状态（槽位、最近推荐、待确认操作、短期偏好），必须设置 TTL 且不得写入敏感信息。
- **不可写**：MySQL、MinIO、Milvus（只在离线脚本中由运维侧更新，不在请求链路中写入）。

## 6. 与 AptInsight 的对比

| 维度 | AptInsight | AptGuide |
|------|-----------|----------|
| 用户 | 运营 / 管理员 | 租客 |
| 调用方 | 管理后台 `rentHouseAdmin` | 移动端 `rentHouseH5`（经 lease 转发）|
| 主要意图 | 经营指标、数据分析 | 找房、预约、咨询 |
| 数据访问 | Text-to-SQL 直查 MySQL | 调 Java 工具接口 + Milvus |
| 关键安全 | SQL 守卫、表白名单 | 用户身份隔离、写操作确认 |
| 输出形式 | 表格、ECharts 选项、总结 | 房源卡片、操作按钮、自然语言 |
| 会话状态 | 可选 Redis 缓存分析上下文 | Redis 保存多轮槽位、最近推荐、待确认操作 |

## 7. 与其他项目的关系

| 项目 | 与 AptGuide 的关系 | 集成阶段职责 |
|------|--------------------|--------------|
| `rentHouseH5` | C 端最终入口 | 提供聊天页面、房源卡片渲染、预约确认弹窗、快捷操作 |
| `lease web-app` | C 端业务网关 | 校验租客 JWT，提供 `/app/ai/chat`，把用户身份透传给 AptGuide |
| `lease internal tools` | 业务工具层 | 封装房源、预约、租约、浏览历史等白名单接口 |
| `rentHouseAdmin` | 运营后台 | 后续维护房源标签、规则知识库、查看 AI 效果指标 |
| `AptInsight` | B 端分析助手 | 分析 AI 带来的预约转化、热门偏好、区域需求和运营问题 |

## 8. 成功标准（MVP 验收）

- 第一阶段：独立 AptGuide 应用可以在浏览器中完成完整对话，包含找房、追问、房源卡片、预约确认、FAQ 来源展示。
- 第二阶段：`rentHouseH5 → lease → AptGuide → lease tools` 链路可联调通过，前端不直接调用 Python 服务。
- 自然语言找房可在 ≤ 3 轮对话内返回有效房源卡片，召回房源全部为 Java 校验后的"可预约"状态。
- 看房预约从需求到落库全程可在 5 轮以内完成，且写操作前 100% 经过显式确认。
- 用户租约 / 预约查询的结果与 lease 直接查询一致。
- 租房 FAQ 回答有依据可溯源（引用知识库条目 ID）。
- 评测集（`evals/datasets/`）整体准确率 ≥ 80%（具体指标见 `07-测试验收方案.md`）。

## 9. 后续路线（非 MVP）

- 个性化记忆（长期偏好沉淀）
- 房源对比助手
- 续约 / 退租流程引导
- 报修助手
- 站内消息整合（推送预约提醒、租约到期提醒）
- 多模态（图片识别、语音输入）
