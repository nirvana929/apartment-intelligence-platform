# 02 · 产品需求文档

## 1. 需求描述

AptGuide 需要分两步建设。

第一步，先做一个**独立可运行的 AptGuide 应用**。它需要有浏览器界面，用户可以在界面中输入自然语言并与智能助手多轮对话。该应用用于验证核心 AI 能力，包括自然语言找房、模糊偏好推荐、房源卡片展示、预约前确认、租约 / 预约查询、租房规则 RAG 问答和 Agent 评测。第一阶段允许使用 Mock / Stub 业务数据，但请求、响应、工具调用和安全确认机制必须按真实系统集成标准设计，避免后续重做。

第二步，再把 AptGuide **集成进现有公寓租赁系统**。最终 C 端入口是 `rentHouseH5`，前端不直接调用 Python 服务，而是通过 `lease web-app` 的 `/app/ai/chat` 入口完成鉴权和转发。AptGuide 通过 `lease` 提供的内部工具接口读取房源、创建预约、查询租约和浏览历史。AptGuide 产生的预约、偏好和对话行为沉淀到业务系统后，可由 `AptInsight` 在 B 端做运营分析，形成 C 端智能找房和 B 端智能分析的闭环。

## 2. 阶段范围

| 阶段 | 目标 | 入口 | 数据来源 | 验收重点 |
|------|------|------|----------|----------|

## 4. 功能详细说明

### 4.1 独立聊天应用

**用户目标**

- 在浏览器中打开 AptGuide 独立页面。
- 像真实租房助手一样输入问题、继续追问、查看房源卡片、点击快捷操作。
- 在不依赖 `rentHouseH5` 和完整 Java 联调环境的情况下演示核心 AI 能力。

**界面能力**

1. 聊天消息列表：区分用户消息、助手消息、工具错误提示。
2. 输入框：支持发送自然语言问题。
3. 房源卡片：展示标题、租金、区域、标签、图片、可预约状态。
4. 操作按钮：查看详情、预约看房、换一批、继续筛选。
5. 确认区域：预约等写操作必须展示摘要并等待用户确认。
6. 来源展示：FAQ 回答展示知识库条目 ID 或标题。

**约束**

- 第一阶段 UI 可以调用 AptGuide 自身的 `/api/chat`。
- 第一阶段可以使用 Mock / Stub 工具实现，但响应结构必须与第二阶段保持一致。
- 独立 UI 只用于演示、开发和评测，不承担最终生产入口。

### 4.2 自然语言找房

**输入示例**

- "我预算 3000，想住天河区，最好支持月付"
- "想找一个安静一点、适合备考的房子"
- "帮我推荐一个房子"

**Agent 行为**

1. 抽取显式条件：`max_rent`、`district`、`payment_type`、`lease_term`、`tags`。
2. 若关键条件（预算 + 区域）缺失，先追问；否则进入召回。
3. 调用 `vector.room_index.search` 做语义召回，得到候选 `room_ids`。
4. 调用 Java `room.search` 做精确过滤，剔除已下架、价格不符等。
5. 取前 3~5 个房源，调用 LLM 生成推荐理由。
6. 返回结构化响应：自然语言 + 房源卡片数组 + 快捷操作。

**约束**

- 一次最多返回 5 个房源。
- 推荐理由必须基于卡片中已有字段，不允许编造配套或评价。

### 4.3 看房预约

**输入示例**

- "帮我预约第一个房源明天下午看房"
- "预约 302 房间，5 月 3 号下午 3 点"

**Agent 行为**

1. 抽取槽位：`room_id`（可指代上一轮房源）、`appointment_time`、`remark`。
2. 时间不精确（"明天下午"）时追问具体时段。
3. 槽位齐全后，**先不写**，返回操作摘要：

   > 已为你准备预约：天河公寓 302 房间，5 月 3 日下午 15:00。**确认预约吗？**

4. 用户确认后，调用 Java `appointment.create`。
5. 把后端返回的预约号、状态如实回传。

**异常**

- 时间冲突 / 房源不可预约 / 用户已存在同时段预约 → 直接告知失败原因，不重试。

### 4.4 我的租约 / 我的预约

**输入示例**

- "我的租约什么时候到期"
- "我现在有几个预约"

**Agent 行为**

1. 跳过 Milvus，直接调用 Java `user.leases` / `user.appointments`。
2. Java 内部按 `X-User-Id` 过滤，只返回当前用户数据。
3. 用自然语言总结，关键日期、状态高亮。

### 4.5 租房规则 FAQ

**输入示例**

- "怎么预约看房"
- "押金怎么退"
- "可以提前退租吗"

**Agent 行为**

1. 调用 `vector.kb_search.search`，从 `apt_rental_kb` Collection 召回相关条目（top-k=3）。
2. 把召回内容拼接进上下文，由 LLM 生成回答。
3. 若涉及具体租约（如"我的押金还能退多少"），同时调用 Java 租约接口取真实数据。

**约束**

- 回答末尾附"信息来源"标签（条目 ID 或标题），便于运营审核。
- 召回相似度低于阈值时，回退到"我没有直接答案，建议联系门店"，不强答。

### 4.6 系统集成与数据闭环

第二阶段集成后，AptGuide 与其他项目的交互方式如下：

1. `rentHouseH5` 提供最终用户入口，复用现有房源卡片和预约页面能力。
2. `lease web-app` 新增 `/app/ai/chat`，负责校验 `access-token`，从 `LoginUserHolder` 获取用户身份，再调用 AptGuide。
3. AptGuide 不信任前端传入的 `user_id`，只信任 `lease` 通过内部请求头透传的 `X-User-Id`。
4. AptGuide 调用 `lease internal tools` 完成房源精确过滤、预约创建、租约查询和浏览历史查询。
5. AI 创建的预约建议在业务数据中标记来源，如 `AI_CHAT`，便于 `AptInsight` 后续分析 AI 转化效果。
6. `rentHouseAdmin` 后续可维护房源标签和规则知识库，变更后通过同步脚本更新 Milvus。

## 5. 对话样例

### 样例 A：模糊偏好找房

```
用户：想找安静一点、适合考研的房子。
助手：好的，我先按"安静、适合备考"为你筛选。能告诉我预算范围和希望的区域吗？
用户：3000 以内，天河区。
助手：为你找到 3 个比较合适的房源：
       1. 天河公寓 302 — 月租 2800，独卫，朝南，周边安静
       2. 科韵公寓 506 — 月租 2950，靠近图书馆，月付
       3. 棠德公寓 412 — 月租 2700，户型紧凑，地铁 6 号线
       想看哪一个的详情，或者直接预约看房？
```

### 样例 B：预约前确认

```
用户：帮我预约第 1 个，明天下午。
助手：明天下午有 14:00 / 15:00 / 16:00 三个时段可选，你希望几点？
用户：3 点。
助手：好的，准备为你创建预约：
       房源：天河公寓 302
       时间：2026-05-02 15:00
       是否确认？
用户：确认。
助手：预约成功，预约号 A20260502302。届时门店会有专人接待。
```

### 样例 C：租约查询

```
用户：我的租约什么时候到期？
助手：你目前有 1 份在租租约：
       公寓：科韵公寓 506
       起租：2025-08-01
       到期：2026-07-31
       距到期还有 92 天，到期前 30 天可申请续约。
```

### 样例 D：FAQ

```
用户：提前退租会扣押金吗？
助手：根据租房规则，提前退租分两种情况：
       · 距到期 ≤ 30 天：押金按原条款全额退还。
       · 距到期 > 30 天：扣除一个月违约金，剩余押金退还。
       具体以你签订的合同为准。
       — 来源：租房规则 / 退租政策（KB-RULE-008）
```

## 6. 输入输出契约

### 6.1 第一阶段请求（独立 UI 调用）

```http
POST /api/chat
Content-Type: application/json

{
  "session_id": "demo-s-001",
  "message": "我预算3000，想住天河区",
  "context": {
    "last_recommendations": [3001, 3002]
  }
}
```

第一阶段没有真实登录态时，服务端使用演示用户或 Mock 用户上下文。此模式只允许用于本地开发和演示，不进入生产。

### 6.2 第二阶段请求（由 lease 调用）

```http
POST /api/chat
X-Internal-Token: <shared-secret>
X-User-Id: 10001
X-Request-Id: req-uuid

{
  "session_id": "s-001",
  "message": "我预算3000，想住天河区",
  "context": {
    "last_recommendations": [3001, 3002]
  }
}
```

## 7. 验收标准（节选）

- 独立应用：浏览器界面可完成多轮对话、房源卡片展示、预约确认、FAQ 来源展示。
- 独立应用：无 Java 联调环境时，Mock / Stub 工具可支持核心 happy path 演示。
- 系统集成：`rentHouseH5` 只调用 `lease /app/ai/chat`，不直接调用 AptGuide。
- 系统集成：`lease` 能把已鉴权用户身份透传给 AptGuide，AptGuide 不接受前端 body 中的 `user_id`。
- 数据闭环：AI 预约或推荐行为具备来源标识，后续可被 AptInsight 分析。
- 找房：召回房源 100% 通过 Java 二次校验为"可预约 / 已上架"。
- 预约：写操作前必须出现"操作摘要 + 等待确认"；未确认不允许调用写接口。
- 租约 / 预约查询：返回数据与 Java 直查结果完全一致。
- FAQ：召回相似度低于阈值时不强答；回答末尾必须标注来源。
- 错误处理：上游接口异常时，必须返回明确的失败原因，不得伪造数据。

完整验收清单见 `07-测试验收方案.md`。
