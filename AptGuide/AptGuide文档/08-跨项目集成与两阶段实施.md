# 08 · 跨项目集成与两阶段实施

## 1. 背景与目标

AptGuide 不是一个孤立聊天 demo，而是 `apartment-intelligence-platform` 中的 C 端租房 Agent。它需要先独立成型，再集成到现有公寓租赁系统。

整体需求可以描述为：

> 第一阶段，设计并实现一个独立的 AptGuide 应用。它有自己的浏览器界面，用户可以直接进行多轮对话，完成找房推荐、房源卡片查看、预约确认、租约 / 预约查询和租房规则问答。这个阶段重点验证 Agent 能力、RAG 召回、工具调用协议、写操作确认和评测体系。
>
> 第二阶段，把 AptGuide 集成到现有系统中。最终 C 端入口是 `rentHouseH5`，前端经 `lease web-app` 调用 AptGuide；AptGuide 通过 `lease` 内部工具接口访问真实业务能力，不直接访问 MySQL。AptGuide 产生的 AI 找房和预约行为沉淀到业务数据后，由 `AptInsight` 在 B 端分析转化效果、热门偏好和运营问题。

## 2. 两阶段交付

| 阶段 | 目标 | 入口 | 数据 | 交付物 |
|------|------|------|------|--------|
| 第一阶段：独立应用 | 可演示、可评测、可调试 | AptGuide 自带 Web UI | Mock / Stub 工具数据，Milvus KB，可选 lease 联调 | 聊天界面、Agent API、房源卡片、预约确认、评测集 |
| 第二阶段：系统集成 | 接入真实业务系统 | `rentHouseH5` → `lease /app/ai/chat` | `lease internal tools`、Milvus、Redis、MySQL 间接数据 | Java AI 网关、H5 聊天入口、真实预约落库、AptInsight 分析闭环、Docker Compose |

## 3. 第一阶段：独立应用

### 3.1 用户体验

独立应用提供一个浏览器聊天界面，支持：

- 多轮对话消息列表；
- 用户输入框；
- 房源卡片；
- 查看详情、预约看房、换一批等快捷操作；
- 写操作前的确认摘要；
- FAQ 回答来源展示；
- 工具失败、无结果、召回不足等异常状态展示。

### 3.2 技术边界

```text
AptGuide Web UI
      ↓ /api/chat
AptGuide FastAPI
      ↓
LangGraph Agent
      ├─ Mock / Stub tools
      ├─ Milvus room vector
      └─ Milvus rental KB
```

第一阶段可以不依赖 `rentHouseH5` 和完整 `lease` 环境，但要遵守第二阶段接口模型：

- 请求中有 `session_id`、`message`、`context`；
- 响应中有 `reply`、`cards`、`actions`、`pending_confirmation`、`sources`；
- 工具层有统一接口，Mock backend 和 HTTP backend 可切换；
- 预约等写操作必须经过确认节点。
- 多轮状态通过 Redis 或本地内存适配器保存，接口行为保持一致；
- 支持 SSE 流式响应，展示意图识别、工具调用、增量回答和最终卡片。

### 3.3 验收标准

- 浏览器中可以完成自然语言找房和多轮补全。
- 房源推荐以结构化卡片展示。
- 预约创建前必须出现确认摘要。
- FAQ 回答展示知识库来源。
- 无 Java 环境时也能通过 Mock 工具完成 happy path。
- Agent 评测集能覆盖意图识别、槽位抽取、工具调用和安全确认。
- Prompt 版本变更后能通过评测报告对比效果。
- 日志中能按 `request_id` 追踪一次对话的意图、检索、工具调用和回答。

## 4. 第二阶段：系统集成

### 4.1 C 端链路

```text
rentHouseH5
  ↓ access-token
lease web-app: POST /app/ai/chat
  ↓ X-Internal-Token + X-User-Id + X-Request-Id
AptGuide: POST /api/chat
  ↓
lease internal tools / Milvus
```

集成原则：

1. `rentHouseH5` 不直接调用 AptGuide。
2. `lease web-app` 负责 JWT 校验、用户身份获取、统一响应结构和异常包装。
3. AptGuide 不接受前端 body / query 中的 `user_id`。
4. AptGuide 只信任 `lease` 透传的 `X-User-Id`。
5. 真实业务读写都通过 `lease internal tools` 完成。

### 4.2 B 端链路

```text
rentHouseAdmin
  ↓ access-token
lease web-admin: POST /admin/ai/chat
  ↓
AptInsight
  ↓ readonly SQL
MySQL
```

AptGuide 与 AptInsight 不互相调用。两者关系是：

- AptGuide 负责 C 端交易和服务动作，例如找房、预约、咨询。
- AptInsight 负责 B 端经营分析，例如预约趋势、热门区域、AI 转化率。
- 两者通过 `lease` 业务数据形成闭环。

### 4.3 数据闭环

```text
用户通过 AptGuide 找房 / 预约
        ↓
lease 写入预约、浏览、来源标识
        ↓
AptInsight 分析 AI 预约转化、偏好分布、热门区域
        ↓
运营在 rentHouseAdmin 调整房源标签、规则知识库、推荐策略
        ↓
Milvus 同步房源向量和知识库
        ↓
AptGuide 推荐和问答质量提升
```

建议在真实业务数据中增加或复用来源字段，例如：

- 预约来源：`AI_CHAT`；
- 推荐来源：`AI_GUIDE`；
- 会话 trace：`request_id` / `session_id`；
- 可选埋点：推荐曝光、卡片点击、预约确认、预约成功。

### 4.4 本地联调环境

第二阶段建议提供 Docker Compose，用于降低多服务联调成本：

```text
docker compose up
  ├─ MySQL      业务数据
  ├─ Redis      会话状态 / pending confirmation
  ├─ MinIO      房源图片对象存储
  ├─ Milvus     房源向量 / 规则知识库
  ├─ AptGuide   C 端 Agent 服务
  └─ AptInsight 可选，B 端分析服务
```

`lease` 和前端项目可先保持本地命令启动；后续需要完整演示时再加入 Compose。Docker 不是第一阶段前置条件，但第二阶段应该补齐。

## 5. 项目职责

| 项目 | 职责 |
|------|------|
| `AptGuide` | C 端 Agent 服务；理解用户需求，执行 RAG、工具调用、预约确认和回复生成 |
| `rentHouseH5` | C 端最终界面；渲染聊天、房源卡片、操作按钮和确认弹窗 |
| `lease web-app` | C 端业务网关；鉴权、身份透传、内部调用 AptGuide、包装统一响应 |
| `lease internal tools` | 受控业务工具；提供房源、预约、租约、浏览历史等接口 |
| `rentHouseAdmin` | 运营后台；后续维护规则知识库、房源标签和查看 AI 效果 |
| `AptInsight` | B 端分析 Agent；分析 AI 助手带来的业务结果 |

## 6. 面试叙事

这个项目可以对外描述为：

> 我做的是一个公寓租赁双 Agent 平台。C 端是 AptGuide，负责自然语言找房、RAG 问答、工具调用和预约确认；B 端是 AptInsight，负责 Text-to-SQL 经营分析。两个 Agent 不直接耦合，而是通过 Spring Boot 业务系统和 MySQL 数据闭环连接。AptGuide 第一阶段先做独立可演示应用，第二阶段再接入真实 H5 和 Java 网关，既保证开发效率，也保证最终能落到真实业务链路。

这能体现的大模型应用开发能力：

- Agent 编排：LangGraph 状态机、意图路由、槽位补全、确认节点；
- RAG：Milvus 房源语义召回、租房规则知识库、阈值回退、来源引用、可选重排；
- Tool Calling：Java 工具接口白名单、httpx 客户端、错误映射；
- Memory：Redis 保存多轮槽位、最近推荐、待确认操作和短期偏好；
- Streaming：SSE 展示工具调用进度、增量回答和最终结构化卡片；
- 安全：不直连 MySQL、不信任前端 userId、写操作二次确认、工具白名单；
- 工程化：Mock backend、契约测试、Agent Eval、Prompt 版本管理、JSON 日志、trace_id；
- 系统集成：H5、Spring Boot、Python Agent、Milvus、MySQL、B 端分析闭环。

## 7. 技术栈取舍

| 技术 | 是否引入 | 理由 |
|------|----------|------|
| Redis | MVP 引入 | 支撑任务型 Agent 的多轮状态和待确认操作 |
| SSE | MVP 引入 | 提升 AI 对话体验，也能暴露工具调用进度 |
| Docker Compose | 第二阶段引入 | 解决 MySQL、Redis、MinIO、Milvus、AI 服务联调成本 |
| MCP | 增强路线 | 当工具数量增长后，把 Java 工具和检索工具标准化 |
| Kafka / RocketMQ | 暂不引入 | 仅在房源变更需要事件驱动同步时再上 |
| Kubernetes / Nacos | 暂不引入 | 当前项目重点是 AI 应用能力，不引入服务治理复杂度 |
| 多模态 | 暂不引入 | 可作为后续“看图问房源”，不影响 MVP 主链路 |
